## 〇、摘要

高校宿舍分配长期由「按学号顺序、按班级切块、宿管手工微调」完成。这套做法能保证不出错，但完全不看学生之间是否合得来，也不对学生解释为什么把他分到这里。已有的算法研究要么追求一个分数最优而不可解释，要么停在「按兴趣聚类」的层面，没有回答管理员最常问的那两个问题：**为什么是他？改了会怎样？**

本项目做了一套可运行的系统，把宿舍分配建模成**带硬约束（性别、楼栋、年级、特殊房型、容量）与多目标软项（相容度、志愿、均衡、公平）的分组优化问题**，并围绕「可解释」设计了完整的决策支持链路：

1. **算法**：块分解（利用硬约束把问题拆成互相独立的子问题）→ 贪心构造 → 带桶守卫的局部搜索 → 阻塞对修复。
2. **相容度模型**：11 维心理/生活特征上的两两打分模型，缺失维度有明确语义（未知 ≠ 满分为好）。
3. **解释层**：四层解释——命中哪条约束、相容度分解到具体特征、志愿满足情况、与「别人怎么住」的对比。
4. **反事实申诉**：学生提出「我想和某人住一起」，系统在**三级递进的搜索范围**内试算，并报出**这次改动会让谁搬家、整体目标变化多少**——满足诉求的代价是可量化的，而且必须展示给管理员。
5. **特征抽取**：规则抽取 + 大语言模型抽取 + 两者集成的对比评测（创新点 4）。

**核心结论（均为真实运行产生的数据）**：

- 主实验（36 组配置 × 10 种子 × 4 方法 = **1440 次求解**，100% 硬约束可行）：NEST 相对现有「按学号顺序」做法把**平均相容度提高 9.5%**（p<0.001，Cohen's d=1.94）、把**房内差距压低 28.4%**、把**志愿满足率提高约 15 倍**、**阻塞对减少 7.7%**；代价是单次分配从 2.03 ms 变成 218 ms。相对最强基线（纯贪心）仍全面更优，且**快 18.0%**。
- 用 CP-SAT 精确求解器做裁判（n=200，5 个种子）：NEST 解**5/5 全部被证明为全局最优**，但**平均只要 2.54% 的最优间隙**——启发式在效果上已经站在最优解旁边。
- 规模：n=10000（10000 名学生 / 2509 间房 / 26 个块）**2353 ms** 完成，**0 条硬约束违规、0 人未分配**。
- 324 人的真实形态试点（18 个块、每块恰好住满）跑通：215 ms、0 违规，并实测了两级申诉的成本与边界。

**比上面这些数字更值得写进报告的，是一次自我纠错**：项目验收阶段我们查出一个**评估偏差**——相容度模型原先用总体均值补齐缺失特征，等价于把「这位学生没回答问卷」算成「他很合得来」。改成正确语义后，NEST 在缺失数据上的绝对表现**下降了 3~4 个百分点**，相对基线的领先也随缺失率单调缩小。旧模型下那些更漂亮的数字，是我们自己在给自己发奖。**缺失数据没有免费午餐；系统能做的不是「在数据缺失时依然准确」，而是不假装准确。**（详见 §5.6）

## 一、项目背景与意义

### 1.1 一个每年秋天都要重来一遍的手工活

高校宿舍分配每年涉及数千名学生、上千间房。它必须同时满足一批**不能违反**的硬约束：

- 性别不混住（最硬的底线）；
- 年级不混住（多数学校要求，也有学校允许混合）；
- 特殊需求学生单独楼层/房型（轮椅、安静、低楼层等）；
- 房间容量不得超员，且不能有人没床；
- 专业/学院相对集中（便于管理）。

在此基础上，还有一批**最好满足**的软目标：作息相近、卫生习惯接近、性格合得来、不把有矛盾的人放一间、楼栋意愿、男女朋友（本校不适用）、以及不同块之间的**公平**。

现实中的做法是「按学号排」或「按班级切块」——它把硬约束做得很好（因为它根本不看特征，所以不可能违规），但软目标完全交给运气。常见的后果是：一个 23:30 睡的人和一个凌晨 2 点睡的人被排进同一间四人房，然后一整个学期互相折磨；每学期都有相当比例的学生要求换宿，而宿管只能手工对调。

### 1.2 为什么「可解释」不是锦上添花，而是能不能用起来的前提

我们做过一次关键的判断：**这个系统真正要说服的不是算法，是宿管。**

一个只输出「学生 A 应该住 3 号楼 512」的系统，宿管不敢用。他会问：

- 为什么是 512 而不是 511？（万一 511 更好呢）
- 我想把他和 B 调一起，能不能？**要付什么代价？**
- 这个结果是不是把某几个学生当成了「牺牲品」？

因此本项目把「可解释」当成**功能需求的一等公民**，而不是事后加一段自然语言说明：

- 每条分配都能展开成「**命中/未命中**了哪些约束」；
- 每间房的相容度可以分解到**具体是哪一维特征在贡献、哪一维在冲突**；
- 每个学生都能看到自己房间的**志愿满足情况**；
- 每个学生都可以发起**反事实申诉**：「我想和 TA 住一起」，系统回答的是**在付出多大代价的前提下可以**，以及**要动多少人**——而不是简单说一句「已受理」。

### 1.3 项目来源与基础（如实说明）

本项目最早的想法是「把已有的一套课堂管理系统改造成宿舍系统」。实际执行中我们做了取舍：

- **保留了**原有教学管理系统作为工程基座（Spring Boot + MyBatis + MySQL 的骨架、登录鉴权、部署方式、离线化的多页面前端），因为「让功能先跑起来」是项目早期的明确优先级；
- **但没有依赖**它的业务模型。宿舍算法的核心 `com.umi.nest.dorm` 包是**零 Spring 依赖**的纯 Java 实现，只有 3 处对外引用（统一的 `Result` 返回体）。
  - 实测：`com.umi.nest.dorm.*` 内部 import 191 处，对外 import 3 处。也就是说**算法内核可以脱离 Web 框架单独编译、命令行运行、单元测试**——实验就是用命令行跑的，不启动 Spring。

**诚实地说**：一个教学管理系统和宿舍分配之间的业务关联是弱的，这一点在申报/答辩中容易被质疑。我们的回应是：**创新点不建立在基座上**。块分解、相容度语义、CP-SAT 裁判、三级反事实申诉、心理特征集成抽取，这五件事换任何一套 Web 框架都成立。基座只是省了我们重写登录和部署的时间。

## 二、研究现状与本项目的位置

### 2.1 现实中的主流做法

| 做法 | 硬约束 | 软目标 | 可解释 |
|---|---|---|---|
| 按学号顺序 | 完备 | 无 | 无（「学校就这么排的」） |
| 按班级/专业切块 | 完备 | 几乎没有 | 弱（「你们班在这栋」） |
| 学生自选室友 + 系统凑房 | 依赖填报质量 | 只覆盖室友意愿 | 弱 |
| 宿管手工微调 | 依赖人工 | 依赖经验 | 强（人能解释），但不可复现、不可审计 |

最后一行是关键：**人工分配的可解释性是它唯一的、也是决定性的优势**。任何自动化方案要真正取代手工，必须在可解释性上至少持平，否则管理员没有理由交出决策权。

### 2.2 学术脉络与我们的切入点

宿舍分配在算法上属于**带约束的分组/装箱问题**，一般形式是 NP-hard 的：

- 一类工作走**多目标进化算法**（遗传、粒子群、NSGA-II）：能给出 Pareto 前沿，但**不可解释**、**不可复现**（同一输入两次运行结果可能不同）、规模上去以后解的质量不稳定。对宿管而言，「这代算法随机跑出来的一组宿舍」是无法交付的。
- 一类工作走**稳定匹配（Gale-Shapley 及其变种）**：理论上优美，但稳定匹配的标准形式假设「每个学生能对每个房间排序」并且房间容量为 1——现实中房间容量是 4，且约束是「同一房间内的人要互相合得来」，这是**多对多的分组稳定性**，比标准稳定匹配难得多，而且现实里稳定解往往不存在。我们最终把它转化成了可计算的**阻塞对（blocking pair）**计数——「有多少对室友，如果让他们单独商量、在剩余的房间里换一下，双方都会更满意」。这是一个**可测量、可比较、可向管理员解释**的代理指标。
- 一类工作走**机器学习预测配对结果**：需要历史标签，而历史数据恰恰是「按学号排」的产物，拿它训练等于把现有做法的偏见学一遍。

**本项目的定位**：不追求在某个人为设定的目标函数上刷出更漂亮的数字，而是做一条**「确定性的、可解释的、代价可见的」决策支持链路**：算法给出解 → 解释为什么 → 管理员可以提出反事实问题 → 系统量化回答代价 → 管理员决定是否采纳。

### 2.3 我们明确放弃的两条路线

这两条都写在设计文档里存档，这里如实重申：

- **放弃「多目标进化作为算法主线」**：不是因为它不好，而是因为它与「可解释、可复现」的项目定位冲突。多目标进化的可视化与 Pareto 探索被保留为一个**辅助视角**（管理员可以看质量-均衡的取舍），但**不进主链路**。
- **放弃「端到端学习式分配」**：需要真实标注数据，而本项目在结题阶段拿到的是模拟数据；设计上只留了**可插拔接口**，把学习式方法放到二期。

1. **能跑**：能在数千人规模上稳定产出 100% 满足硬约束的分配方案，且耗时可接受。
2. **更好**：在真值已知的合成数据上，相对现有做法有**统计显著**的质量提升。

4. **能互动**：学生能申诉，系统能算出代价，管理员能看懂代价。

| `dorm_audit` | 审计 | 谁在什么时候改了什么 |
| `dorm_ground_truth` | 实验隐真值 | **只用于实验评估**，生产环境为空 |
| `dorm_psyche_profile` / `_answer` / `_text` / `_eval` | 心理特征 | 问卷、开放文本、抽取结果、人工校正与评测 |

**三个值得强调的数据设计**：

1. **缺失是一等公民。** `dorm_student_feature` 的每一列都可为 NULL，Java 侧映射为 `Double.NaN`；导入接口的 `feature` 用 **`Double[]`（装箱类型）而不是 `double[]`**，因为只有装箱数组才表达得了「第 3 维未知」。用 0 顶替等于把「他什么也没说过」算成「他明确表示不介意」——这是本项目修掉的一个真实缺陷（§5.6）。
2. **志愿按种类独立替换。** 学校导入的名单通常只带楼栋意愿、不带室友意愿。早期实现按学生整体替换，结果一次名单导入把学生自己在门户上填的室友志愿全部擦掉。现在三者独立，且**空列表不等于清空**（「这次导入没说他有什么志愿」≠「他没有志愿」），唯一的全清入口是显式的 `replaceAll=true`。
3. **导入先体检、后写入。** `POST /api/dorm/data/preflight` 是只读的，可以反复试：字段缺失、学号重复、性别认不出、特殊需求取值非法、特征维度全 0（可能是「没回答」被写成了 0）、楼栋不存在、容量对不上——同类问题合并计数并最多举 3 个例子（一千行都缺年级时，要看的是「共 1000 处，例如第 3、7、19 行」，不是一千行日志）。**体检不过 → 一行都不写。**

### 4.3 求解算法

`NestSolver.NAME = "nest-block-greedy-ls-repair-v1"`，四个阶段：

**① 块分解（Block Decomposition）——本项目最能省时间的一步**

硬约束本身蕴含了可分解性：性别不同的学生不可能同住，房型（特殊/普通）不同的学生不能用同一批房间，年级/专业大类是否允许混住由学校策略决定。于是分块键为

```
blockKey = 性别 | S(特殊)或 N(普通) [| 专业大类] [| 年级]
```

（专业大类与年级是否进键，取决于学校策略；特殊需求学生直接独立成块。）

由此得到一个关键性质：**不同块之间的学生永远不会竞争同一个房间，因此块与块之间完全独立、可并行求解。** 在 n=10000 的实例上这直接产生 26 个块，最大块 400 人——问题规模瞬间降了两个数量级。

房间按 `poolKey = 性别 | S/N` 分池，池内按块人数降序分配房间（优先取容量 ≤ 剩余需求的最大房间）。若精确划分失败，**退化成整池合并成一个块并记录 warning**——绝不静默丢人。

**② 贪心构造**

块内按「特征代表性」排序（先放特征明确的学生，让后面的人有参照），逐个插入当前边际代价最小的房间。房间评分包含相容度项、志愿项、避让项。

**③ 带桶守卫的局部搜索**

反复尝试单步移动/交换。**桶守卫（bucket guard）**的作用是防止局部搜索把解「抹平」：如果一次移动只是把一个房间的分数从 0.9 拉到 0.91、却在另一个房间制造了 0.4 的差房，就应该被拒绝。守卫保留解的**分布形状**，避免出现「平均分很高但有一间房是灾难」的结果。

**④ 阻塞对修复**

计算阻塞对（双方单独商量就能都变好、且剩余房间容得下的室友对），针对性地做定向交换。这是「近稳定」定义（创新点 1）的直接落地。

**算法复杂度与实测**：

| 规模 | 块数 | 房间数 | 耗时 | 硬约束违规 | 未分配 | 平均相容度 |
|---|---|---|---|---|---|---|
| 10,000 人 | 26 | 2,509 | **2,353 ms** | **0** | **0** | 0.7609 |

### 4.4 相容度模型

在 11 个维度上建模：睡眠开始/结束、吸烟、卫生、外向性、在房间学习、噪声耐受、社交活跃度、物品共用、游戏、进取心。两两相容度由各维得分加权得到。

**三条设计原则**：

1. **缺失 ≠ 中性。** 某一对室友在某一维上有一方没填，这一维**不参与计算**，而不是按「差异 0」给满分。若一对室友没有任何一维是双方都填过的，这一对**不可评估**——系统明确报「无依据」，而不是打 0.00。
2. **可加性。** 房间质量项设计为**房内所有配对的贡献之和**（而不是「取最差的一对」）。这不是为了算法方便——它使目标函数可以在 CP-SAT 里**精确线性化**（§5.3）。这是本项目「算法设计与验证设计互相咬合」的一处例子。
3. **志愿与避让有方向性。** 「我想和 TA 住」单方面命中 = +1.0，**双方互相填了对方** = +1.5；「不想和 TA 住」是惩罚项。这个权重差让系统更倾向满足「双向奔赴」。

### 4.5 四层解释（创新点 2 的一半）

| 层 | 回答的问题 | 输出 |
|---|---|---|
| 约束层 | 为什么能/不能把他放这儿？ | 逐条列出命中的硬约束（性别、年级、房型、容量） |
| 特征层 | 他和室友合得来吗？具体是什么？ | 逐维贡献排序 + **「冲突最明显的是哪一维」** |
| 志愿层 | 他的意愿被满足了吗？ | 想同住/不想同住/楼栋意愿的逐条命中情况 |
| 对比层 | 别人怎么住的？ | 本房与全体在相容度、方差、公平上的对比 |

**特征层的一个重要细节**（同样是修掉的真缺陷）：早期实现取「贡献排序第一的维度」作为「冲突最明显的维度」，而未知维的贡献恰好是 0，总排第一——于是产出一句自相矛盾的话：「和你冲突最明显的是「吸烟」这一项（与某某，**未知（这一项你们至少有一方没填）**）」。现在会跳过不可评估的维度，取第一个**真的有差异**的维度。

同层还有一个「分母」问题：一间六对室友的房间如果只有一对可评估，早期实现把不可评估的对按 0 混进均值，算出 0.0343 甚至 0。现在只对**可评估的对**求均值与最差，并**同时给出分母**——「平均相容度 0.2056（基于 1/6 对室友）」。学生自己就能看出这个数字有多可靠。

### 4.6 反事实申诉：三级漏斗（创新点 2 的另一半）

学生提出「我想和某人住一起」后，系统**不直接改**，而是试算并报价。三级搜索范围由小到大：

| 级别 | 搜索范围 | 典型耗时 | 代价 |
|---|---|---|---|
| 一级：房间级 | 只重排目标房间内部 | 毫秒级 | 通常 0~1 人轮换 |
| 二级：块级 | 在申诉人所在的块内重解 | 数十毫秒 | 可能动多人 |
| 三级：跨块级 | 合并两个块 + 放宽政策约束（年级不混住 / 专业大类集中）后重解，**异步执行** | 数十至数百毫秒 | 动十几到上百人 |

**三级的设计要点**：

1. **必须先做硬约束可行性判定。** 如果两人性别不同，系统直接说「在你的硬约束下不可能」，而不是让搜索空转。
2. **放宽项必须点名。** 早期实现在失败路径上返回空的放宽列表，消息却说「即使放宽**上述政策**」——指向一个从未列出的东西。现在 `Relaxation(flag, label, why)` 会明确写出「放宽了「年级不混住」，因为你和希望同住的同学不在同一个年级，而当前策略要求同一房间内年级一致」。
3. **必须报代价，且代价有两个维度**：目标函数变化量 **和** 波及人数。只报其中一个都是误导。实测（§5.5）：同一个诉求在房间级只要动 1 个人，跨块级要动 **13 个人**——代价的差别在这里，不在分数上。
4. **多一个口径**：整实例的软目标会被 96% 没动的房间稀释，所以同时报「只看这次真正碰过的那几间房」的版本，否则数字变化根本看不出来。
5. **最后一道闸**：任何建议在返回前都要过 `SolutionValidator.validate(problem, cfg, patched)`——没有房间超容量、没有人被弄丢。**软目标里看不见超容量**（软目标不算硬罚项），所以这一步不能省。

**「在我搜过的范围里没找到」不等于「无解」。** 这句话是系统输出的一部分。跨块级已经是本系统最大的搜索范围，如果它没找到，系统就诚实地说没找到，并声明这不构成无解证明。

### 4.7 心理/生活特征抽取（创新点 4）

学生可以用自然语言描述自己的生活习惯（「我睡得比较晚，一般两点左右，有点烟瘾，室友抽烟我无所谓」），系统从中抽取 11 维特征。三路对比：

| 路线 | 机制 |
|---|---|
| RULE | 关键词 + 规则匹配，确定性、零成本 |
| LLM | 大语言模型结构化抽取，每维给 few-shot 锚点，多采样取均值以量化不确定性 |
| ENSEMBLE | 两者集成 |

**三条工程约束**（都是踩出来的）：

1. **隐私在出口处擦除。** 学生文本在送往外部大模型之前必须脱敏（去掉姓名、学号、手机号等），擦除发生在**出站边界**，而不是靠调用方自觉。
2. **对话解析只认「自己说的话」。** 解析多人对话时，只把该学生自己发出的轮次作为输入，否则会把室友的生活习惯算到他头上。
3. **缺失就是 NULL。** 抽取不出来就留 NULL，绝不用默认值补齐——同样是因为默认值会被下游当成「他说过了」。

### 4.8 多端交付

学校要的是「多端跨平台」，本项目用三条路径回答：

1. **PC 管理端**：完整功能（导入、体检、分配、审计、参数、申诉审批）。
2. **学生端 PWA**：`manifest.webmanifest` + Service Worker + 安装按钮。可安装到手机桌面、离线壳可用。核心学生流程（看分配、填志愿、填问卷、发起申诉）在手机上可用。
3. **微信端**：规划中。学生端已经全部是**标准 HTTP REST + 无框架前端**，接微信小程序/公众号只需换一层壳，不需要改后端——这是当初坚持不引入重前端框架的原因。

**PWA 的一个真实坑**：`manifest.webmanifest` 必须以 `application/manifest+json` 提供，否则浏览器不认安装。Spring Boot 默认按扩展名给 `application/octet-stream`，`spring.mvc.media-types` 配置项无效，`MediaTypeFactory.addFileExtension` 在 Spring 6.1.4 里不存在——最后用一个显式声明 `produces` 的 Controller 解决。

### 4.9 离站化与部署

**全部页面离线化**（学校内网往往不能访问公网）：

- Tailwind 从 CDN 改为**预编译本地 CSS**（`nest.css`，扫描全部 21 个页面）；
- 字体从 Google Fonts 改为**本地文件**（正文用 Public Sans 的局部字重；Material Symbols 图标字体最初裁成 185 个字符的小子集，**后因子集漏字形而上过屏，2026-10-09 换成全量 4301 个图标名的字体，323 KB**，见《课堂管理系统-功能补全说明》§7.3）；
- 第三方库本地化（如二维码生成库 `qrcode.min.js`）；
- 一个曾经把文件内容发给 Google Docs Viewer 在线预览的页面，改为**不发送任何数据**的本地提示。

**离线化的一个真实教训**：删掉 Tailwind CDN 的 `<script>` 之后，页面里残留的内联 `tailwind.config` 脚本块会抛 `ReferenceError: tailwind is not defined`。而页面**看起来还是能显示的**（大部分样式来自本地 CSS），所以这个错误极易漏过。现在的清理脚本会**一并删除内联配置块**。

**部署**：`mvn package` 产出单个可执行 jar（35,266,979 字节），`java -jar` 即可；配置通过 `config/local.properties` 外置（含数据库口令、大模型 API Key）；`docs/给学校的部署说明.md` 有 10 节完整说明，含「学生到底要提交什么」的四级漏斗表和已知限制清单。

## 五、实验与验证

> 完整数据与复现命令见 `docs/实验与验证.md`；原始报告在 `target/exp-*.md`。
> **所有数字均为真实运行产出，没有任何一个数字是估算或「应该能达到」的。**

### 5.1 实验设计

**为什么要造数据**：真值已知才能算「绝对正确率」。真实宿舍分配没有客观的「正确答案」——这也是这个领域难以评测的根本原因。所以实验用**合成数据**，其中每个学生的**真实相容度结构 `g`** 是已知的，而算法只能看到被**噪声污染**的**观测特征**。这使得「算法的解在真值下的质量」可以计算。

**四个待比较的方法**：

| 代号 | 方法 | 代表什么 |
|---|---|---|
| B0 | 按学号顺序 | **现有系统的做法**（最重要的对照） |
| B1 | 块内随机 | 随机下界 |
| B2 | 纯贪心构造 | 最强的朴素算法 |
| NEST | 完整算法 | 本项目 |

**七个评估指标**：均值相容度、最差那对、房内方差、志愿满足率、阻塞对数、公平差距、耗时。

**配对纪律**：配对单位是 **(配置, 种子)**——同一配置同一种子下，四个方法面对的是**完全相同的输入**。用 Wilcoxon 符号秩检验 + 配对 t 检验双报告。

**一个容易被忽略的统计限制**：样本量 n 很小时，Wilcoxon 能达到的最小 p 值是 `2^(1−n)`。n=5 时最小 p = 0.0625 —— **无论效果多大都不可能达到 0.05**。所以消融实验（5 个种子）我们**不报显著性**，只报数值差异和效应方向；并在报告里写明「此处的种子数不足以做出显著性判断」。不报，比报一个假的强。

### 5.2 主实验：规模 × 噪声 × 缺失率 × 紧张度

**36 组配置** = 学生数 {1000, 5000} × 观测噪声 {10%, 25%, 45%} × 特征缺失率 {0%, 25%, 50%} × 房间紧张度 {0.2, 0.8}，每组 10 个种子，4 个方法，共 **1440 次求解**，耗时 **393.8 秒**，**全部 100% 硬约束可行、无一人未分配**。

**表 1 汇总（全部 360 个（方法, 配置, 种子）格子）**

| 方法 | 均值相容度 | 最差那对 | 房内方差 | 志愿满足率 | 阻塞对数 | 公平差距 | 耗时(ms) |
|---|---|---|---|---|---|---|---|
| B0 学号顺序（**现有系统**） | 0.6371 ± 0.0042 | −0.0943 | 0.0156 | 0.0038 | 5046.95 | 0.0185 | 2.03 |
| B1 块内随机 | 0.6365 ± 0.0038 | −0.0818 | 0.0158 | 0.0037 | 5046.47 | 0.0188 | 2.04 |
| B2 纯贪心 | 0.6897 ± 0.0275 | −0.1078 | 0.0115 | 0.0578 | 4666.62 | 0.0183 | 266.04 |

| 指标 | 变化 | p | d | 结论 |
|---|---|---|---|---|
| 均值相容度 | **+1.1%** | <0.001 | 1.30 | **显著更优** |

| 阻塞对数 | **−0.2%** | <0.001 | −0.54 | **显著更优** |
| 公平差距 | +0.1% | 0.9788 | 0.00 | 无显著差异 |
| 耗时 | **−18.0%** | <0.001 | −0.49 | **显著更优** |

**怎么读这组数（三条，都要说）**：

1. **对现有做法是压倒性的，对最强基线是稳健的。** 对 B0 的效应量 d≈1.94，不是「勉强显著」而是明显分层；对 B2 是全面小胜，但**七个指标里五个显著更优、零个显著更差**。
2. **代价是时间，但要说清量级。** 2.03 ms → 218 ms 是约 **107 倍**。数字很大，但换算成场景：**一次分配 0.2 秒**，而这件事**一学期只做一次**。把 0.2 秒说成缺陷是误导；把「快 107 倍」当成优势也是误导——**在这个场景下时间根本不是约束**。真正的约束是「结果能不能被接受」。
3. **两个没赢的指标要主动交代。** 最差那对对 B0 是 −8.3%（不显著，p=0.26），公平差距 −1.2%（不显著）。见 §6「没赢的地方」。
4. **意外收获：NEST 比 B2 快 18%。** 直觉上「更聪明的搜索」应该更慢。原因是局部搜索先构造出更整齐的解，后续阻塞对修复要处理的冲突少了，**总时间反而下降**。

### 5.3 与 CP-SAT 精确最优解的对比（创新点 1 的硬证据）

「NEST 的解到底有多好」不能只跟其他启发式比——那样只能说明「比其他启发式好」。我们用 Google OR-Tools 的 **CP-SAT**（精确求解器）做裁判。

**为什么能精确建模（这一步不是显然的）**：因为 §4.4 选择把房间质量定义成**房内所有配对贡献之和**，目标函数对「某一对是否同房」是线性的，可以用布尔变量 `x[i][r]` 和配对变量 `z[i][j]` 精确表达：

```
z[i][j] ≤ x[i][r]        z[i][j] ≤ x[j][r]
z[i][j] ≥ x[i][r] + x[j][r] − 1     （z = AND(x,x) 的标准线性化）
```

如果质量项取「房内最差的一对」（那才是直觉上更合理的定义），目标里就会出现 min/max，**无法精确线性化**，整个裁判就做不成。这是一个「算法设计被验证能力反向约束」的例子，我们在设计文档里把它记为一条明确的取舍。

**结果（n=200，5 个种子）**：

| 种子 | NEST 耗时 | CP-SAT 耗时 | 最优间隙 | 是否被证明最优 |
|---|---|---|---|---|
| 1 | 43 ms | 4100 ms | 2.65% | ✅ |
| 2 | 14 ms | 1598 ms | 2.39% | ✅ |
| 3 | 10 ms | 2984 ms | 2.18% | ✅ |
| 4 | 9 ms | 2507 ms | 3.12% | ✅ |
| 5 | 7 ms | 2366 ms | 2.35% | ✅ |

**5/5 全部被证明全局最优，平均仅差 2.54%，而 NEST 快两个数量级。** 注意措辞：这 2.54% 不是「NEST 达到了最优」，而是「**在裁判能证明最优的那些实例上**，NEST 的解离最优有多远」——这是**上界**。

**规模的边界（诚实报告）**：

- n=400：CP-SAT 跑 144.4 秒仍**未能证明最优**，只能给出 **1.45% 的间隙下界**（下界的意思：真实差距可能比这大得多）。原因是一个 29 人的块容量**没有恰好住满**，无法施加「每间房正好满」的强化约束。
- n=1000：CP-SAT 在 8.1 秒时**主动拒绝**——该实例需要 **24,795 个布尔变量，超过 15,000 的预算**。我们选择拒绝而不是让求解器跑几个小时，因为「跑不出来」对用户毫无价值。

**两条把「证不出来」变成「秒级可证」的建模经验**（这是本项目在 CP-SAT 上最实在的收获）：

1. **加一条隐含的强化约束能让证明时间从 150 秒变成零点几秒。** 早期对块 `F|N|经管类|2025`（16 人 / 544 个变量）跑了 **150,484 ms 仍未能证明最优**。加上两条由问题结构隐含的约束后——「当块容量恰好等于块人数时，每间房必须正好住满」——**全部 26 个块在 4,052 ms 内全部证明完毕**，且最优目标值一模一样（185.741）。求解器不缺算力，缺的是**人告诉它这个问题的结构**。
2. **一个方向写反的线性化会伪装成「问题无解」。** CP-SAT 在一个**显然可行**的实例上返回 INFEASIBLE，我们用 6 个最小变体做二分定位，最后发现问题出在 AND 线性化的第三条约束：写成了 `z ≤ x_i + x_j − 1`（应为 `z ≥ …`），等价于**强制每一对都是室友**。这个错误最阴的地方是：两种写法在求解器的中间表示里**代数等价**，proto 层检查根本看不出来，只能靠设计最小复现实验来区分。

### 5.4 大模型特征抽取评测（创新点 4）

**n=60 条真值，每个学生 8 条文本送大模型，采样 2 次**：

| 指标 | RULE | **LLM** | ENSEMBLE |
|---|---|---|---|
| MAE（越低越好） | 0.207 | **0.118** | 0.139 |
| \|Pearson\| | 0.806 | **0.846** | 0.833 |
| \|Spearman\| | 0.646 | **0.726** | 0.695 |
| 崩溃率（越低越好） | 1.470 | **1.048** | 1.161 |
| 覆盖率 | 78.4% | **96.6%** | 96.6% |
| 耗时 | **40 ms** | 60,795 ms | 61,492 ms |

**结论**：**大语言模型在每一个质量指标上都优于规则**，尤其是覆盖率（78.4% → 96.6%）——规则抽取的短板正是「学生用规则没预料到的说法」。**但集成并没有赢过大模型单独使用**，这是一个反直觉的负面结果，我们如实保留：一个弱规则组件拖累了强 LLM 组件。

**代价是 1500 倍的时间**（40 ms → 61 秒）。这棵树要不要种，取决于文本量：对几十条文本，60 秒完全可接受；对全校几千条，需要批处理与缓存策略。**系统设计上两者都保留，由管理员选择**——而不是替学校做决定。

### 5.5 反事实申诉的实测（创新点 2 的证据）

在 **324 人试点实例**（18 个块，每块恰好住满）上实测：

**用例 A：同块内不同房**（吴可欣 980 在女生1号楼-101，希望与 张雨轩 974 在女生1号楼-102 同住）

| 级别 | 结果 | 耗时 | 代价 |
|---|---|---|---|
| 房间级 | **SATISFIED** | 49 ms | 目标变化 **−0.3609**（预算 0.5，在预算内） |
| 跨块级 | **SATISFIED**，放宽项：无 | 19 ms | 目标 −32.4401 → −32.8010，**要动 13 位同学**（合并块 20 人 / 5 间房） |

系统给出的具体建议是：「把 吴可欣 与 赵诗琪 对调即可（女生1号楼-101 ⇄ 女生1号楼-102）」——**一个可以直接执行的单一操作**，而不是一段解释。

**注意这里最有意思的一点**：两级的目标变化量**完全相同**（−0.36），差别全在**波及人数**（1 人 vs 13 人）。这就是为什么「代价」必须同时报两个维度——只报分数的话，管理员会以为两级一样便宜。

**用例 B：跨年级**（吴可欣 980 希望与 王欣怡 1013 同住，两人同专业大类但不同年级）

| 级别 | 结果 | 耗时 | 输出 |
|---|---|---|---|
| 房间级 | **UNSATISFIABLE** | 0 ms | 「这条诉求在你的硬约束下不可能满足：王欣怡 与你年级不同（硬约束：年级不混住）」 |
| 跨块级 | **NOT_FOUND_IN_SCOPE** | 91 ms | 放宽项：**「年级不混住」**（并说明为什么需要放宽）；「重解后仍然没有和你住到一起……**「在我搜过的范围里没找到」不等于「无解」**，但这一级已经是本系统最大的搜索范围」 |

这就是「可解释」在实践中的样子：**系统知道了自己的能力边界，并把边界说了出来**，而不是含糊地说「无法满足」。

### 5.6 一次自我纠错：缺失数据没有免费午餐

这是本项目在验收阶段自己查出来的、也是最值得写进报告的问题。

**问题**：相容度模型的构造函数用**总体均值**补齐每一个缺失维度（`StudentFeature.imputed(mean)`）。

**为什么这是错的**：均值补齐会让**所有没答同一道题的学生变得完全相同**——差异 0.00 → 相容度 1.00。也就是说，**越是不填问卷的学生，系统越认为他们志同道合**。对求解器而言这是一个**虚构的吸引力**，它会主动把这些人凑到一间房。旧模型在缺失率高的实验组里表现「更鲁棒」，不是因为算法好，而是因为**它在拿一个自己虚构出来的高分**。

**改法**：缺失位保持未知；相容度只在**双方都填过的维度**上计算；一维都没填的对标记为**不可评估**（不是 0 分）。解释层与门户同步改成报「平均相容度 = null，可评估 0/6 对」。

**代价（按规模 × 缺失率分组，旧模型 → 新模型）**：

| 规模 | 缺失率 | B2 | NEST |
|---|---|---|---|
| n=1000 | 0% | 0.7064 → 0.7064（+0.00%） | 0.7235 → 0.7235（−0.01%） |
| n=1000 | 25% | 0.6895 → 0.6723（−2.48%） | 0.7030 → 0.6813（**−3.09%**） |
| n=1000 | 50% | 0.6722 → 0.6590（−1.96%） | 0.6851 → 0.6610（**−3.51%**） |
| n=5000 | 0% | 0.7382 → 0.7382（0.00%） | 0.7491 → 0.7490（−0.00%） |
| n=5000 | 25% | 0.7145 → 0.6918（−3.18%） | 0.7233 → 0.6970（**−3.65%**） |
| n=5000 | 50% | 0.6908 → 0.6704（−2.96%） | 0.6996 → 0.6726（**−3.86%**） |

**两件事同时成立，都要写进报告**：

1. **缺失 0% 时所有方法逐位不变**（NEST 差 0.0001）。这说明改动是**外科手术式**的——它只影响有缺失的格子，不是把整个模型换掉了。
2. **缺失越多，NEST 相对最强基线 B2 的领先越小**：n=5000 时 **+1.46% → +0.75% → +0.33%**。旧模型下这个领先看起来对缺失「免疫」——那不是鲁棒。

**结论**：缺失数据没有免费午餐。**系统能做的不是「在数据缺失时依然准确」，而是不假装准确**——把「这一对学生没有任何可比依据」如实报出来，让学校知道该去催问卷，而不是拿一个虚高的相容度糊弄过去。

### 5.7 消融实验：每个设计决策值多少钱（n=1000，5 种子，8 个方法）

| 去掉什么 | 结果 | 结论 |
|---|---|---|
| 木桶项（桶守卫） | 0.7284 vs NEST 0.7286 | **基本无差别（负面结果）** |
| 专业大类分块 | **每个质量指标都更好**（志愿满足 0.2009 vs 0.0688，约 **2.9 倍**） | 见下 |
| 局部搜索 | 相容度 −1.4%，但**最差那对更好**（−0.0108 vs −0.0624），且**快 3.8 倍** | 见下 |

**三个诚实的结论，两个是负面的**：

1. **木桶项在本实验设定下没有可测收益。** 我们保留它是因为它防的是「平均分高但有一间房灾难」的分布风险，而实验指标（房内方差、最差那对）没能把它区分出来。**这是负面结果，如实记录。**
2. **「专业大类集中住宿」是一条政策要求，不是质量改进——它的价格是可测量的。** 放开分块后，志愿满足率从 0.0688 涨到 0.2009（约 2.9 倍）。为什么？因为**放宽分块让学生的备选范围从「同专业同年级」扩大到「同性别全部」**，他的室友志愿更容易被满足。这不是算法变好了，是**约束松了**。价值在于：**学校第一次可以看到「专业集中」这条规定的代价是多少**——这是一个可以直接放进管理决策的结论。
3. **局部搜索在「平均」上是正收益、在「最差」上是负收益。** 它把平均相容度提高了 1.4%，但把最差的那一对做得更差（−0.0624 vs −0.0108），并且慢 3.8 倍。也就是说局部搜索倾向于**把好的房间做更好**，而不是**救援差的房间**。这解释了为什么木桶项没能体现收益——**守卫的意图和局部搜索的行为没有对齐**。这是本项目一个明确指向未来的改进点。

## 六、创新点

### 创新点 1：容量约束下的「近稳定」可计算定义

宿舍分配里「稳定」这个古典概念不好直接搬用（容量 4、多对多）。本项目把它转化为**可计算、可解释、可比较**的形式：

- 以**阻塞对**为核心指标：有多少对室友，如果让他们单独商量并在剩余房间里互换，双方都会更满意；
- 用 **CP-SAT 精确最优解**作为参照上界，把「离最优有多远」变成一个可以量化报告的数（实测 n=200 上平均 2.54%）；
- 诚实承认**零阻塞对在容量 4 下通常不可达**，且判定它本身是 NP-hard 的——所以目标是「更少」，不是「为零」。

**创新之处不在于用了阻塞对，而在于把它做成了一个能被独立验证的裁判体系**：目标函数被刻意设计成可精确线性化的形式（可加性），使精确裁判成为可能。

### 创新点 2：可解释 + 反事实申诉的闭环

把「解释」从输出文本升级为**可交互的决策支持**：

- **四层解释**覆盖约束、特征、志愿、对比；
- **三级反事实申诉**从「只动目标房间」递进到「跨块重解 + 政策放宽」，每一级都给出**可执行的建议**（「把 A 与 B 对调即可」）而不是一段自然语言；
- **代价必须双维度可见**：目标函数变化量 **+ 波及人数**。实测证明这是必要的——同一个诉求在房间级动 1 人、跨块级动 13 人，而目标变化量**完全相同**；
- **搜索范围透明**：「在我搜过的范围里没找到」不等于「无解」，系统把这条边界写进输出。

### 创新点 3：利用约束结构的问题分解

把硬约束本身当作可分解性的来源：按 `性别 | 房型 | 专业大类 | 年级` 分块，块间完全独立。这不是一个「加速技巧」，而是一个**结构性结论**——它同时带来了：

- 规模下降（n=10000 → 最大块 400 人）；
- 可并行（块之间零交互）；
- 可解释（「你和这批人竞争房间」有了确切含义）；
- 可裁判（CP-SAT 能逐块精确求解，才使 §5.3 的裁判成为可能）。

### 创新点 4：心理特征抽取的三路对比与「不假装准确」的缺失语义

- 规则 / 大模型 / 集成三路在同一真值集上对比，**完整报告负面结果**（集成不如单用大模型）；
- **隐私在出站边界擦除**、**只解析学生自己的对话轮次**、**抽取不出就留 NULL** 三条工程纪律；
- 与创新点 1/2 联动：**缺失语义贯穿模型、解释、门户三层**——不只是一处代码修复。

### 创新点 5（方法论）：把「验证能力」作为设计约束

本项目最有价值的一条经验是：**算法设计要为「可被验证」留出空间**。

- 目标函数取「配对贡献之和」而非「最差那一对」，牺牲了（直觉上）一点合理性，换来的是**精确裁判的可能性**；
- 实验用合成数据而非真实数据，牺牲了生态效度，换来的是**真值可计算**；
- 消融只有 5 个种子时明确声明「不足以做显著性判断」，牺牲了好看的表，换来的是不撒谎。

## 七、应用价值与推广

### 7.1 直接价值

1. **可交付**：单 jar 部署、六条命令的离线化构建链、10 节部署文档、导入前体检与「导入会/不会动什么」对照表——学校信息中心拿到就能上。
2. **可解释**：管理员能看到每条分配的依据，学生能看到自己房间的志愿满足情况与相容度分解——**这是宿管愿意交出决策权的前提**。
3. **可审计**：每次分配、每次申诉、每次参数调整都有审计记录，批次可回溯。
4. **代价可见**：反事实申诉让「我想换宿」从「求宿管帮忙」变成「系统告诉你这件事要动多少人、值不值」——**降低管理摩擦，而不是增加**。

### 7.2 推广路径

- **多校适配**：约束由 `ConstraintConfig` 与数据驱动（是否分块、权重、预算、容量），改配置不改代码；
- **多端扩展**：学生端全部是标准 REST + 无框架前端，接微信小程序/公众号只需换壳；
- **离线可用**：全部前端资源本地化，适配内网/校园网环境；
- **可复用到其他分组问题**：本项目的算法与可解释框架同样适用于班组分派、实验分组、导师分配、值班排班——这些都是「硬约束 + 多目标 + 需要解释」的同构问题。

## 八、存在的问题与不足（诚实清单）

**这一节不是走过场。以下每一条都是我们真实遇到、并且选择写出来的。**

1. **没有 Dorm 模块的单元测试。** `src/test` 现有 10 个测试文件（2476 行）**全部属于基座教学系统**，`com.umi.nest.dorm` 的验证靠的是实验脚手架（命令行）与端到端 HTTP 探针。这在结题阶段可以接受（有 1440 次求解的实验证据），但**工程上是一个明确的缺口**：算法内核的回归保护依赖实验而不是断言。
2. **真实学籍数据试点是形态化模拟，不是真实数据。** 324 人试点用的是我们按真实形态构造的名单（真实专业名、真实学号格式、真实缺失模式、真实志愿比例），数据库独立（`nest_pilot`）。**它验证的是链路与规模，不验证模型在真实学生上的效果。** 要验证后者，需要学校提供脱敏历史数据 + 真实的换宿申请记录。
3. **`n=400` 以上无法证明最优。** CP-SAT 在 n=400 上跑 144 秒仍只给出 1.45% 的**下界**（真实差距可能大得多），n=1000 直接因变量预算超限被拒绝。所以「NEST 距离最优多远」这个结论**只在 n=200 上有硬证据**。
4. **跨块级申诉在 40 人满编块上可能找不到解。** 实测用例 B：放宽「年级不混住」、合并 40 人 / 10 间、全部恰好住满，仍然 `NOT_FOUND_IN_SCOPE`。原因是块内是贪心 + 局部搜索，可能需要**非单步改进的链式重排**才够得着。系统诚实报「没找到」并声明不构成无解证明，但**这是一个可以被改进的算法弱点**（可行方向：申诉子问题上加一次精确求解或多起点重启）。
5. **集成抽取没有赢过大模型单用。** 覆盖率与各项指标都是 LLM 最好、ENSEMBLE 居中——一个弱规则组件拖累了强组件。我们没有为了「集成」这个词粉饰结果。
6. **木桶项在消融中没有可测收益，且局部搜索的行为与它的意图没有对齐。** 局部搜索倾向于把好房间做得更好（最差那对反而变差），而桶守卫本意是救援差的房间。这是**一处已定位、未解决的设计不一致**。
7. **楼栋意愿存了两处，可能不一致。** `dorm_preference(BUILDING)` 与 `dorm_student.building_pref` 都存楼栋意愿，学生在门户上修改只更新前者，后者会停在导入时的版本。**分配结果本身是正确的**（求解器只读前者），但如果有报表直接读后者，会看到旧值。
8. **公平性只有「差距」指标，没有做严格的公平性理论分析。** 我们报公平差距（专业/年级维度上的最大-最小差），但没有证明任何公平性性质。当前实证结果是 NEST 与基线**无显著差异**（不是更好）。
9. **前端是被验证过的，但不充分。** 前端验收是 curl + DOM 探针 + 截图级验证，**没有浏览器级的自动化端到端测试**（如 Playwright 套件），也没有做无障碍与真机兼容性矩阵测试。
10. **微信端只有规划，没有实现。** 「多端跨平台」目前交付的是 PC + PWA 两端。
11. **实验用的是合成数据。** 生态效度受限：真实学生的特征是相关的、非正态的，噪声结构也未必是实验里假设的那样。这削弱了「+9.5% 在真实场景也成立」的外推力度。
12. **大模型抽取的成本未优化。** 60 秒对几十条文本可用，对全校几千条需要批处理与缓存——目前只有设计，没有实现。
13. **申诉失败路径的代价数字位是占位 0。** `CrossBlockAppeal.Trial` 在「没排出方案」的三条失败路径上把
    `objectiveBefore/objectiveAfter/objectiveDelta/moveCount` 一律写成 `0.0`，于是原始 JSON 里
    一次真的重解了 40 人的试算看起来是「目标 0.0000 → 0.0000、移动 0 人」。**管理端界面已经修掉**
    （只在 `status=SATISFIED` 时才渲染代价两行，否则显示「本次试算没有产出可采纳的调整方案，因此不报代价、
    也不报波及人数」），演示脚本也按同一原则处理；但**直接读接口的第三方消费者仍可能被误导**。
    正确读法是：**判定一律以 `status` 为准，只有 `SATISFIED` 才有代价可言**。彻底修法是把这几个字段
    改成可空（`Double` / `Integer`），但会动到 JSON 契约，本次未做。

---

## 九、结论

本项目把宿舍分配从「按学号排的手工活」做成了**一条可运行、可解释、代价可见的决策支持链路**，并在真值已知的数据上给出了统计显著的改进证据：

- 相对现有做法，**平均相容度 +9.5%（p<0.001，d=1.94）、房内差距 −28.4%、志愿满足率约 15 倍、阻塞对 −7.7%**；代价是 2.03 ms → 218 ms——在「一学期一次」的场景下不构成约束；
- 相对最强基线，**五个指标显著更优、零个显著更差，并且快 18%**；
- CP-SAT 裁判证明：在 n=200 上 NEST 的解**5/5 被证明全局最优，平均仅差 2.54%**；
- 10000 人规模 2.35 秒完成，0 违规、0 未分配；324 人形态化试点跑通全链路含两级申诉。

比这些数字更有价值的，是三条**方法论层面的收获**：

1. **验证能力必须参与算法设计。** 目标函数取「配对贡献之和」这个看似不如「最差那一对」的定义，恰恰是让 CP-SAT 精确裁判成为可能的前提。**能被验证的设计，才是能被证明好的设计。**
2. **诚实的负面结果比漂亮的正面结果更有信息量。** 集成不如单用大模型、木桶项没有可测收益、局部搜索在「最差」上反而更差、公平性没有改进——这四条我们都写在报告里。它们每一条都指向一个具体的改进方向。
3. **最需要警惕的是「自己给自己发奖」。** 缺失数据那一节（§5.6）里，旧模型更漂亮的数字来自一个系统性偏差：把「没回答」当成「很合得来」。我们花了力气把它找出来、修掉，代价是报告里的数字变小了。**缺失数据没有免费午餐；一个决策支持系统最重要的一种能力，是知道自己在什么情况下没有依据，并且不假装有。**

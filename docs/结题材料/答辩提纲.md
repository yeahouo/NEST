# 答辩提纲（NEST · 安居）

> 配 12~15 页 PPT。括号内是建议时长。**每一页只讲一件事，数字都是从报告里直接抄的，没有一个需要现场估算。**

---

## 一、开场（30 秒）

**一句话**：我们把「按学号排宿舍」这件每年秋天要重做一遍的手工活，做成了一套**能跑、更好、说得清、能互动**的决策支持系统。

**要先说清的两件事**（避免评委先入为主）：

1. 我们的重点不是「用 AI 分宿舍」，而是**「让一个自动化方案能真正被宿管接受」**——所以可解释和代价可见是功能需求，不是附加说明。
2. 所有效果数字都来自**真值已知的合成数据 + 1440 次真实求解 + CP-SAT 精确裁判**，并且我们主动报告了一次**自己查出来的评估偏差**。

---

## 二、问题（1 分钟）

**页 2：宿舍分配到底难在哪**

必须满足的硬约束（性别、年级、房型、容量、专业集中）↔ 最好满足的软目标（作息、卫生、性格、矛盾避让、志愿、公平）。现有做法（按学号排）把硬约束做得很好——**因为它根本不看特征**——但软目标完全交给运气。

**页 3：真正的障碍不是算法，是信任**

宿管会问三个问题：

- 为什么是他？→ 需要解释
- 我想换，行不行？**要付什么代价？** → 需要反事实试算
- 是不是有人被当成了牺牲品？→ 需要公平指标

**这个系统真正要说服的不是算法，是宿管。** 任何只输出「A 应该住 512」的系统都不会被采用。

## 三、我们做了什么（1 分钟）

**页 4：一张架构图**

```
多端（PC 管理端 / 学生端 PWA）→ 46 个 REST 端点 → 服务层 → 算法内核（零框架依赖）→ MySQL 14 张 dorm_* 表
```

**页 5：四层解释 + 三级申诉**（本项目的心脏）

- 四层解释：约束层 / 特征层 / 志愿层 / 对比层
- 三级申诉：房间级 → 块级 → 跨块级（+ 放宽政策，异步）
- **代价必须同时报两个维度：目标函数变化量 + 波及人数**

## 四、演示（2 分钟）

**页 6：演示截图或用预录视频**（脚本见 `演示脚本.md`）

演示顺序（**每一步都有真实输出，不要现场重跑长任务**）：

1. 管理端：数据概况 → 导入前**体检**（故意给一份有错的名单，看它逐条点名）
2. 导入 → 分配 → 审计页（谁在什么时候改了什么）
3. **单学生四层解释**：约束命中 / 相容度分解到具体特征 / 志愿满足 / 与全体对比
4. **申诉三级**：同级同块 → 房间级 1 人轮换给出「把 A 与 B 对调即可」；跨年级 → 「不可能，原因是年级不混住」+ 跨块级点名放宽项
5. 学生端 PWA 手机上打开、**断网仍能显示离线壳**

## 五、证据（3 分钟，本次答辩的核心）

**页 7：主实验规模**

36 组配置 × 10 种子 × 4 方法 = **1440 次求解**，393.8 秒，**100% 硬约束可行、0 人未分配**。

**页 8：结果表**（背下这 4 个数字）

| | 现有系统 B0 | 最强基线 B2 | **NEST** |
|---|---|---|---|
| 平均相容度 | 0.6371 | 0.6897 | **0.6974** |
| 耗时 | 2.03 ms | 266 ms | 218 ms |

- **NEST vs 现有系统：+9.5%（p<0.001，d=1.94）、房内差距 −28.4%、志愿满足率约 15 倍、阻塞对 −7.7%**
- **NEST vs 最强基线：五个指标显著更优、零个显著更差，并且快 18%**

**页 9：CP-SAT 精确裁判（最硬的一块证据）**

n=200 / 5 个种子：**5/5 全部被证明全局最优**，平均只要 **2.54%** 的最优间隙；CP-SAT 花 1.6~4.1 秒，NEST 花 7~43 毫秒。

**页 10：规模**

n=10000（10000 人 / 2509 间房 / 26 个块）→ **2353 ms**，0 违规、0 未分配。

**页 11：自我纠错（这一页最能加分）**

我们发现相容度模型原先用**总体均值补齐缺失特征**，等价于「没回答问卷 = 很合得来」——**越不填问卷的学生，系统越认为他志同道合**。改成正确语义后，NEST 在缺失数据上的表现**下降 3~4 个百分点**，相对基线的领先从 +1.46% 缩到 +0.33%。

> **旧模型那些更漂亮的数字，是我们自己在给自己发奖。**
> **缺失数据没有免费午餐；系统能做的不是「在缺失时依然准确」，而是不假装准确。**

## 六、创新点（2 分钟）

**页 12：五个创新点（每条一句话）**

1. **容量约束下「近稳定」的可计算定义**——以阻塞对为核心指标，并用 CP-SAT 给出可验证的参照上界。
2. **可解释 + 反事实申诉的闭环**——三级搜索范围，代价双维度可见，搜索范围透明（「没找到」≠「无解」）。
3. **利用约束结构的问题分解**——块分解不只是加速技巧：它同时带来规模下降、可并行、可解释、**可裁判**。
4. **特征抽取的三路对比 + 贯穿三层的缺失语义**——含完整报告的负面结果（集成不如单用大模型）。
5. **方法论：把「验证能力」当作设计约束**——目标函数刻意取「配对贡献之和」而非「最差那一对」，正是为了让它**能被 CP-SAT 精确线性化**。

**页 13：创新点 5 展开**（如果时间够，这页最容易被记住）

> 「能被验证的设计，才是能被证明好的设计。」
> 我们为了「可验证」主动付了代价：目标函数选了一个直觉上稍弱的形式、实验选了合成数据而非真实数据。这些取舍是**为了换来真值可计算、最优性可证明**。

---

## 七、不足（1 分钟，主动讲，不要等评委问）

**页 14：六条最重要的不足**

1. **Dorm 模块没有单元测试**——验证靠实验脚手架和端到端探针，工程上是缺口。
2. **真实数据试点是形态化模拟，不是真实学籍数据**——它验证链路与规模，不验证真实学生上的效果。
3. **n=400 以上无法证明最优**（只给 1.45% 的下界），「离最优多远」只在 n=200 上有硬证据。
4. **跨块级申诉在满编块上可能找不到解**（局部搜索需要非单步改进的链式重排）。
5. **集成抽取没有赢过大模型单用**；**木桶项消融无收益，且与局部搜索行为不对齐**。
6. **微信端只有规划没有实现**；公平性只报差距，没做理论分析。

**页 15：结论**

> 相对现有做法：**相容度 +9.5%（d=1.94）、房内差距 −28.4%、志愿满足 15 倍**；10000 人 2.35 秒；n=200 上距最优 **2.54%**。
> 但比这些数字更重要的，是**我们找出了自己模型里一个把「不知道」算成「很合得来」的偏差，并且修掉了它**。

## 附录：可能被问到的问题与回答

**Q1：这不就是用了优化算法吗？创新点在哪？**
优化算法本身不是创新——创新在**把「稳定性」变成可计算可验证的形式**（阻塞对 + CP-SAT 参照上界），以及**把「解释」做成可交互的反事实试算**，后者在同类工作里很少见。另外块分解不是一个「加速技巧」，而是后面能把精确裁判做成的前提。

**Q2：CP-SAT 都能精确求解了，为什么不直接用它？**
因为规模。n=200 它要 1.6~4.1 秒，n=400 跑 144 秒还证不出最优，n=1000 需要 24795 个布尔变量、直接被预算拒绝。而 NEST 在 n=10000 上 2.35 秒。**CP-SAT 的角色是裁判，不是生产线**——它用来告诉我们启发式离最优有多远，而不是拿来出结果。它也没有被打进交付的 jar。

**Q3：合成数据有什么意义？真实数据上还能 +9.5% 吗？**
合成数据是**为了能算真值**。真实宿舍分配没有客观正确答案，这正是这个领域难评测的根本原因。我们诚实地说：**+9.5% 是合成数据上的结论，外推到真实场景的力度是有限的**——合成数据的特征更独立、噪声结构更理想。要验证真实效果，需要学校提供脱敏历史数据 + 真实换宿记录，这是我们明确的下一步。

**Q4：学生乱填怎么办？**
三层防御：① 特殊需求走辅导员通道，不靠自报（误报代价不对称）；② 想同住/不想同住有上限（各 ≤5）且双向权重更高（+1.5 vs +1.0），鼓励真实互选；③ 缺失一律存 NULL 并如实显示，问卷填得少的学生会看到「可评估对数 1/6」——**系统不会因为数据少而假装了解他**。

**Q5：隐私怎么保证？**
学生文本在**出站边界**（送外部大模型之前）统一脱敏，去掉姓名/学号/手机号；解析多人对话时**只取学生自己发出的轮次**；抽取结果存本地库。脱敏在出口做，不靠调用方自觉。

**Q6：为什么有两个「没赢」的指标？**
因为诚实。最差那对对 B0 是 −8.3%（p=0.26，不显著），公平差距 −1.2%（不显著）。这两个都在报告的「没赢的地方」一节里，并且指向了具体的改进方向：局部搜索倾向于把好房间做得更好（最差那对 −0.0624 vs −0.0108），与桶守卫「救援差房」的意图**没有对齐**。

**Q7：为什么「专业大类集中住宿」放开后质量反而变好？那这条规定是不是没意义？**
不是「算法变好」，是**约束松了**——学生的备选范围从「同专业同年级」扩大到「同性别全部」，室友志愿从 0.0688 涨到 0.2009（约 2.9 倍）。这条结论的价值恰恰在于**把一条管理规定的价格算了出来**（代价约 80 ms vs 40.8 ms，以及志愿满足率上的差额），学校可以据此决定要不要保留。

**Q8：和课堂管理系统是什么关系？是不是在别人的系统上套壳？**
如实回答：保留了它作为工程基座（登录、部署、多页面前端），但**没有依赖它的业务模型**。算法内核 `com.umi.nest.dorm` 是**零 Spring 依赖**的纯 Java，只有 3 处对外引用；192 处 import 里 191 处都在包内。所有实验都是命令行跑的，不启动 Spring、不连数据库。**创新点不建立在基座上**——换任何 Web 框架，这五个创新点都成立。

**Q9：多端跨平台做到哪一步了？**
PC 管理端 + 学生端 PWA（可安装、可离线）已交付；微信端是二期规划。之所以敢说「接微信只需换壳」，是因为学生端全部是标准 REST + 无框架前端。另外全部前端资源已本地化（Tailwind 预编译、字体子集、库本地化），能适配学校内网。

**Q10：0.2 秒和 2 毫秒差 107 倍，这个开销能接受吗？**
场景换算后完全无感：**分配一次 218 毫秒，而这件事一学期做一次**。在这个场景里时间根本不是约束，真正的约束是结果能不能被接受。反过来也要说清：**我们不会把「快 107 倍」当成优势**——那同样是误导。

**Q11：你怎么知道你的解释是对的？**
解释不是自由文本，而是从**结构化数据**生成的：约束命中来自 `SolutionValidator` 的逐条判定，特征贡献来自相容度模型的逐维分解，代价来自**对同一实例重算软目标**的前后差值。申诉的建议会经过 `SolutionValidator.validate` 全实例校验（无超容量、无丢人）才返回。

**Q12：如果现在给你真实数据，还要做什么？**
① 用真实脱敏数据重跑主实验（重点看缺失率的真实分布）；② 用真实换宿申请记录检验「申诉预测」的准确性；③ 补 Dorm 模块单元测试；④ 把跨块级申诉的局部搜索换成精确求解或多起点重启；⑤ 大模型抽取做批处理与缓存。

**Q13：一句话总结你最大的收获？**
> **最需要警惕的是「自己给自己发奖」。** 我们最漂亮的那组数字来自一个系统性偏差——把「没回答」当成「很合得来」。找出来、修掉它，代价是报告里的数字变小了。但一个决策支持系统最重要的一种能力，是**知道自己在什么情况下没有依据，并且不假装有。**

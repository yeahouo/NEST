# NEST 高校宿舍智能分配与可解释决策支持系统 — 设计文档

- **正式题目**：《高校宿舍智能分配与可解释决策支持系统》
- **项目代号**：NEST（Near-stable Explainable Student-housing maTching），中文「安居」
- **文档日期**：2026-09-27
- **项目根目录**：`D:\project\NEST`
- **性质**：大学生创新创业训练计划（大创）项目

---

## 1. 项目概览

用一个可计算、可解释、能在万级规模上跑动的算法，替代学校现有"问卷 + 规则"宿舍分配方案，解决**室友不匹配**这一核心痛点，并交付一套学工/后勤真正能用起来的系统。

**一句话定位**：不是"又一个管理系统"，而是**一个把宿舍分配形式化为"带容量的近稳定室友匹配"问题、并配套可解释与反事实申诉机制的算法研究 + 工程落地双交付项目**。

**双交付**：
- **研究侧**：算法贡献（近稳定定义、块分解、求解算法）+ 严谨的仿真实验与基线对比
- **工程侧**：PC 管理端 + 微信生态学生端 + 可解释报告 + 申诉工作流

## 2. 背景与约束

### 2.1 现状
学校已有一套系统或脚本（问卷 + 规则/算法），但**效果一般、抱怨不少**。

### 2.2 核心痛点（用户确认为唯一核心）
**室友不匹配** —— 住到一起之后才发现冲突，集中在作息、抽烟、卫生、性格四个方面。

### 2.3 约束条件（均为硬约束，来自用户确认）

| 约束 | 内容 | 对设计的影响 |
|---|---|---|
| **规模** | 上万人 / 尚不清楚 | 必须按可扩展设计；整数规划只能当小规模校验器，不能当主力 |
| **工期** | 一年后结项，但需在 **3 个季度（约 9 个月）内完成**，Q4 作缓冲 | 必须砍范围（见 §7） |
| **数据** | 一个都还没落实，需去找学工处/后勤谈 | **研究主路径不得依赖真实数据**（见 §10 合成数据） |
| **实证能力** | 碰不了真人，只能纯仿真 | 实验设计的严谨性成为唯一可信度来源 |
| **学校支持度** | **有** —— 指导老师就在学工/后勤/宿管线上，或学院明确支持配合 | 数据谈判的钥匙；落地路径据此设计 |
| **跨平台** | **PC 网站 + 微信（学生端）** | 见 §5.4 |

## 3. 创新点

> 三项创新点即使**完全拿不到真实数据**也成立 —— 这是本项目在数据不确定下的最大保险。

### 创新点 1：容量约束下的「近稳定」可计算定义

经典稳定室友匹配（Stable Roommates with Ties, SRTI）要求**不存在阻塞对（blocking pair）**，即"互相想住一起却没被分到一起"的两名学生。

现实困难：
- 容量为 4 的宿舍分组下，**零阻塞对通常不可达**
- 判定本身是 **NP-hard**

**我们的处理（诚实且可证明）**：不承诺"稳定"，而是提出**「近稳定」的可计算定义** —— **最小化阻塞对数量**，并**量化**结果与理论最优之间的距离。用 CP-SAT 在小规模上求真正最优解作为上界参考，回答"我们离最优还有多远、还剩多少阻塞对"。

### 创新点 2：可解释 + 反事实申诉机制

- 每条分配都给出**四维解释**：约束命中、相容度分解到具体特征、志愿层、对比层（见 §9）
- 申诉场景下给出**反事实解释**：固定其余人、在**明确的局部范围内**重解，回答"满足你的诉求会牺牲谁、整体目标下降多少"
- **搜索范围透明**：明确告知"在多大范围内找过"，不承诺全局最优

宿舍分配领域很少有人做反事实解释，这是可讲、能实现、且答辩戳不破的表述。

### 创新点 3：利用约束结构的问题分解（块分解）

先按硬约束把全体学生切成**互不干扰的块**（性别 × 楼栋 × 专业大类），块间无约束交叉，块内独立求解并可并行。

**这不只是工程技巧，本身可作为论文一节**：利用宿舍问题的约束结构做问题分解，把 NP-hard 的全局问题化为可并行的子问题族 —— 这是万级规模唯一跑得动的办法。

---

### 3.4 方案选型：考虑过并放弃的路线

| 方案 | 内容 | 结论 |
|---|---|---|
| **方案 1 稳定性 + 可解释（研究内核）** | 形式化为带容量的稳定室友匹配（SRTI），核心承诺"近稳定"；贪心构造 + 稳定性修复的局部搜索，CP-SAT 小规模校验 | **✅ 选为算法主线**。创新点最硬、不依赖真实数据；代价是理论门槛最高 |
| 方案 2 多目标进化 + 决策支持（工程内核） | NSGA-II / ε-约束求 Pareto 前沿，让辅导员在多个方案间拍板 | 算法本身不新；但**可视化与 Pareto 展示并入系统**（见 §7.2） |
| 方案 3 学习增强 | 双塔 / GNN 学习兼容度 + 匹配 | **依赖真实历史数据**，数据为零时是自证循环。**已落地线性学习基线** `LearnedCompatibility`（纯 Java 岭回归，隐真值上 MAE 比规则版低 ~39%、相关 +0.085）；非线性双塔/GNN 仍留 Phase 2（见 §7.3、§7.4） |

## 4. 问题形式化

### 4.1 输入

**学生集合 `S`（n 人）**

| 类别 | 字段 |
|---|---|
| 硬属性 | 性别、专业/班级、年级、特殊需求（无障碍、宗教饮食、医疗） |
| 软特征 | 作息（入睡/起床时点）、烟酒、卫生习惯、性格自评 |
| 偏好 | 想和谁同住 / 不想和谁同住、想去哪栋/楼层/房型 |

**房间集合 `R`**：容量 `c`（通常 4）、所属楼栋、性别限制、设施配置。

### 4.2 硬约束

- 性别与房间匹配
- 特殊需求房间匹配
- 政策约束：教学班集中、留学生配比、年级不混住
- 容量不超

**硬约束违规数必须恒为 0，否则方案不可用。**

### 4.3 目标函数（两个聚合都要保留）

| 项 | 含义 | 说明 |
|---|---|---|
| `Σ` 房间内两两相容度 | 整体质量 | 现有系统大概率只做了这个 |
| `min`（最差那一对） | **木桶效应** | **现有系统几乎一定没做 —— 这是关键区别** |

另含志愿满足项与违规罚项。

### 4.4 稳定性与近稳定

- **blocking pair**：互相想住一起、却没被分到一起的一对
- **稳定**：不存在任何 blocking pair
- **现实**：容量 4 下零阻塞对通常不可达，且判定 NP-hard
- **近稳定（本项目采用）**：最小化阻塞对数量，并量化与下界的间隙

## 5. 系统架构

### 5.1 分层

| 层 | 职责 | 关键设计 |
|---|---|---|
| **数据层** | 导入学生名单/问卷/房间资源，清洗、校验 | 所有约束走**配置文件**，绝不硬编码 |
| **模型层** | 特征编码、相容度函数、目标函数组装 | 相容度函数**可插拔**：默认规则版 `RuleBasedCompatibility` + 线性学习基线版 `LearnedCompatibility`（已落地），预留非线性双塔/GNN 接口 |
| **求解层** | 出分配方案（核心） | **分级求解**：块分解 → 贪心构造 → 局部搜索修复阻塞对 |
| **评估层** | 算指标、跑基线、出稳定性审计报告 | 4 条基线（见 §10.2） |
| **交互层** | 约束配置、一键分配、可视化、可解释报告、申诉调整 | 申诉 = 固定其余人局部重解，实时显示"会牺牲谁" |

### 5.2 三个决定成败的设计决策

**① 块分解** —— 万级规模唯一跑得动的办法。按硬约束切块（性别 × 楼栋 × 专业大类），块内独立求解、可并行。

**② 约束可配置** —— "能真给学校用"的前提。每校/每学院规则都是本地化的，硬编码 = 只能给一所学校用。规则做成配置文件，辅导员自己就能改。

**③ 本地部署、数据不出校** —— 谈数据时的**决定性说服点**。学工处最怕学生隐私外流；系统离线跑在学工处机器上，不联网、不调云端 API。

### 5.3 技术栈（依据现有资产 `demo2` 确定）

| 层 | 选型 | 依据 |
|---|---|---|
| 后端 | **Spring Boot 3.2.3 + Java 17 + MyBatis 3.0.3 + MySQL** | 与现有 `demo2` 一致；国内高校信息系统标准栈，易被学校信息中心接手 |
| 鉴权 | Spring Security（+ 现有微信绑定能力） | `demo2` 已有 `SecurityConfig`、`BindWechatDTO` |
| 管理端 | **Vue3 + Element Plus**（PC 浏览器） | `demo2` 前端与 `education` 项目均用 Vue + Element Plus |
| 学生端 | **uni-app 一套代码** | 先编译 H5（微信里点链接即开，零资质零备案），条件成熟后编译微信小程序，不用重写 |
| 求解器 | **独立 Maven 模块 + 命令行**，CP-SAT 用 `com.google.ortools:ortools-java` | **求解器与界面彻底解耦**：界面没做完，算法实验照常出结果 |

### 5.4 跨平台决策（PC 网站 + 微信）

**已定策略**：学生端用 uni-app **先出 H5 顶着，小程序当升级项**。

两个必须记住的约束：
1. **微信小程序只能请求已 ICP 备案的 HTTPS 公网域名**，不能请求 IP 或内网地址 → 与"数据不出校"直接矛盾。**解法**：公网只放极小接口层（学生凭学号查自己的房间号与室友、提交申诉），核心数据、全部学生信息、求解算法**全部留在内网**；公网接口拿不到他人数据。
2. **个人主体注册的小程序不能做教育类服务**，必须用**学校或学院的组织主体**注册 → 这是一条依赖学校审批的关键路径，因此**不能让它成为主路径的阻塞点**。

## 7. 范围（MoSCoW）

### 7.1 必须做（Must）

算法核心（块分解 + 贪心 + 局部搜索 + 阻塞对修复）· 评估体系 + 4 条基线 · 数据导入 · 约束配置 · 一键分配 · 结果导出 · 可解释报告 · 学生端查结果 + 提申诉

### 7.2 应该做（Should）

可视化热力图 · CP-SAT 校验 · 申诉处理界面 · 多候选方案 · Pareto 展示

### 7.3 可以做（Could，随时可砍）

学习型兼容度接口（**线性基线已落地**） · 微信小程序 · Tauri 桌面包 · 公平性审计报告

### 7.4 明确不做（Won't）

| 不做 | 理由 |
|---|---|
| 学习型兼容度**实装（非线性双塔/GNN）** | 数据为零 + 时间不够。**已落地线性岭回归基线**，非线性双塔/GNN 仍 Phase 2 |
| 申诉时**全局重解** | 万级全局重解要几十秒到几分钟，申诉场景体验不可接受 → 降级为局部试算 |
| 多学期滚动优化 | 只在开学前跑一次；学期中只支持手工调整 |
| 精细权限体系 | 只分"管理员 / 学生"两种角色，够用 |
| 原生 App | H5 顶住 |
| 分布式多机并行 | 单机多进程 + 块分解足够 |
| 严格稳定性理论证明 | 只做阻塞对计数与间隙量化 |
| 花哨大屏可视化 | 热力图 + 冲突标记 + 导出，够用就行 |

### 7.5 执行规则

**进度落后时，从下往上砍（Won't ← Could ← Should），绝不动 Must。**

## 9. 可解释性与申诉机制

### 9.1 为什么是刚需

分配结果要公示，学生必然质疑"凭什么"。**室友不匹配 + 不知道为什么 = 申诉潮**。可解释性直接换算成辅导员的工作量。

### 9.2 三层可解释

**第 1 层：每条分配的解释（"为什么是这个房间"）**

| 维度 | 内容 |
|---|---|
| 约束层 | 哪些硬约束决定了结果：性别、专业集中、无障碍房、年级政策，逐条列出 |
| 相容度层 | 与每位室友的相容度**分解到具体特征**：作息接近 +0.8、抽烟冲突 −0.5、卫生 −0.3 |
| 志愿层 | 第几志愿；未满足原因（该楼栋床位被更高优先级占满 / 你填的室友自己填了别人） |
| 对比层 | 次优是什么、差多少（"次优是 X 栋 302，相容度低 12%"） |

> **工程要点**：解释**提前批量算好存起来**，不要实时重算。每条解释计算量 `O(房间人数)`，全校算一遍是秒级；让学生点开时现算就会卡。

**第 2 层：申诉的反事实解释（核心卖点）**

固定其余人、局部范围内试算，给出三选一的回答：

1. **能满足**：要动谁、谁的利益受损、整体目标下降多少、是否新增阻塞对
2. **不能满足**：给出硬理由（床位满 / 性别不匹配 / 会破坏硬约束）
3. **在我找过的范围内不能满足**

> **关键设计：分层试算 + 范围透明**
> - 先试**房间级**（毫秒级，实时出结果）
> - 不行再试**块级**（千人块，几秒，异步通知）
> - 明确告知**"我在多大范围内找过"**（例："3 号楼范围内无解，已扩大到 A 区"）
>
> 范围太小 → 常报"无解"其实全局有解，学生更愤怒；范围太大 → 慢。范围透明本身即可解释性，且诚实、不承诺全局最优。

**第 3 层：整体方案的解释（辅导员/公示用）**
- 全校指标报告：志愿满足率、平均/最差相容度、阻塞对数量
- **公平性审计**：是否存在某专业/性别/年级系统性吃亏（答辩加分项，也是学工处最在意的）
- 报告导出 Excel/PDF，直接附在公示里

### 9.3 申诉工作流

```
学生提申诉
   ↓
系统自动试算 → 给出「可行性 + 代价」
   ↓
辅导员看到一个【排好序的队列】：能解决且代价小的排前面
   ↓
一键采纳 → 系统自动局部调整 → 自动重新审计
   （确认没引入硬约束违规、没显著恶化他人）
```

价值：辅导员从"每个人都要解释半天"变成"处理一个有序队列"。

### 9.4 总代价预算（必须加的约束）

申诉**不能无限采纳**，否则整体持续恶化，系统被"会哭的孩子"绑架，反而成为新的不公平。

**机制**：设总代价预算（或每栋楼可调名额）；预算用完，只给解释、不给方案。

### 9.5 两个诚实边界（写进 UI 和论文）

1. **反事实结论是局部的**，不是全局最优承诺 —— 范围多大就说多大。
2. **相容度来自问卷，本质有噪声** —— 未填维度按中性处理**并在解释里标注**，不假装知道。

## 10. 实验设计

> 答辩最可能的质疑：**"你拿自己造的数据、又用自己的相容度函数评估，这不是自证循环吗？"** 本节专门回答它。

### 10.1 合成数据生成器（带隐真值）—— 整个实验的地基

**算法看到的世界与评估用的世界，必须是两个东西：**

```
① 生成真实特征 z_i          作息/烟酒/卫生/性格/专业（从真实分布采样）
        ↓
② 定义真值相容度 g(z_i,z_j)   ← 【算法永远看不到】
        ↓
③ "发问卷" → 观测 o_i = f(z_i) + 噪声   ← 【算法只能看到这个】
        ↓
④ 用真值 g 评估最终结果       ← 【所有指标在 g 上算，不在算法的 compat 上算】
```

**为什么不是自证循环**：算法在噪声观测 `o` 上做决策，评估在真值 `g` 上算分数，两者不同源。

**两个必须做对的地方**：
1. **真值 `g` 必须比算法的 `compat` 更复杂**（否则是"考自己出的题"）：应包含**交互项**（晚睡 × 早起 = 大冲突，不是简单相减）与**未观测隐变量**（问卷问不到的性格部分）
2. **噪声与缺失是可控参数**，用于做**敏感性分析**："问卷噪声变大时我们还赢吗？"

### 10.2 基线

| 基线 | 是什么 | 作用 |
|---|---|---|
| **B0 现有系统复刻** | 按学校规则复刻：专业集中 + 简单志愿匹配 + 随机填空 | **主对手** |
| B1 纯随机 | 满足硬约束的随机分配 | 下界 |
| B2 贪心 | 按志愿/相容度贪心填房 | 证明局部搜索优于贪心 |
| B3 CP-SAT 最优 | 小规模（≤200 人）真最优 | **裁判**：回答"离最优多远" |

> **B0 的坑**：我们没有现有系统代码 → **按规则描述复刻**，论文里写明"基于规则描述复刻"。这顺带又是一条找学工处要**现有系统输出日志**的理由。

### 10.3 指标（全部在真值 `g` 上算）

| 类别 | 指标 |
|---|---|
| 相容度 | 平均值、**最差那一对**（木桶）、房间内方差 |
| 志愿 | 满足率（分第几志愿）、未满足原因分布 |
| **稳定性** | **阻塞对数量（核心指标）** |
| 硬约束 | 违规数 —— **必须恒为 0** |
| 公平性 | 各专业/性别/年级满意度分布差异 |
| 效率 | 运行时间、内存 —— **必须报**，万级是卖点 |

### 10.4 实验矩阵

| 维度 | 取值 |
|---|---|
| 规模 | 1k / 5k / 10k / 20k |
| 问卷噪声 | 低 / 中 / 高 |
| 缺失率 | 0% / 20% / 40% |
| 志愿紧张度 | 宽松 / 紧张 |
| 随机种子 | **≥ 30 次** |

每组跑 4 条基线 + NEST，报告**均值 ± 标准差**并做显著性检验（配对 t 检验 / Wilcoxon）。

> "30 个种子 × 多个规模 × 多个噪声水平"本身就是答辩时最硬的东西 —— 说明不是跑一次碰巧赢了。

### 10.5 消融实验（答辩必问"哪个部件起作用"）

- 去掉**块分解** → 质量与时间的权衡
- 去掉**阻塞对修复** → 阻塞对数量涨多少
- 只用 `Σ` 去掉 `min` 项 → **最差室友相容度掉多少** ← 直接证明"关心木桶效应"有用
- 三级递进：贪心 / 贪心+局部搜索 / 贪心+局部搜索+修复

### 10.6 结论模板（论文摘要可直接套用）

> 在 n=10000、问卷噪声中等、缺失率 20% 的条件下，NEST 相比现有规则复刻版：**阻塞对数量下降 X%、最差室友相容度提升 Y%、平均相容度提升 Z%、志愿满足率提升 W%**，运行时间 T 秒；在 n=200 上与 CP-SAT 最优解相比间隙为 V%。

### 10.7 诚实边界（写进 Limitations）

1. 这是**仿真结论**，只能说"在仿真环境下"，不能说"真实学校会提升 X%"
2. **合成数据的分布假设是最大软肋** —— 用敏感性分析削弱它，并写明：这正是必须争取真实数据做影子运行的理由

## 11. 落地路径

### 11.1 落地是与开发并行的线，不是最后一步

**第 1 个月就去找指导老师要这三样东西**（对他成本极低，成功率高）：

| 要什么 | 用来干什么 |
|---|---|
| 现有系统**规则说明** + 一份**历史输出表**（脱敏） | 复刻 B0 基线（实验的主对手） |
| 一份**新生问卷空白模板** | 让我们的字段和现实对齐 |
| 历史**调宿/矛盾记录**（哪怕只有几十条） | **最珍贵**：能把学习型兼容度从 Phase 2 提前 |

**同时争取：下一次分宿舍的「影子运行」机会** —— 学校照旧分，我们也算一版，两版对比但不影响真实结果。

**为什么影子运行是枢纽**：
- 对学校**零风险** → 容易批
- 拿到真实数据和真实对比 → 论文从"仿真结论"升级为"真实案例"
- **即使我们的方案更差，也是诚实结果，照样能结题**

### 11.2 数据要不到怎么办 —— 退路是设计好的

| 情形 | 项目变成什么 | 结题档次 |
|---|---|---|
| 拿到全部（规则 + 历史 + 影子运行） | 算法 + 系统 + **真实案例** | 优秀 |
| 只拿到规则 + 影子运行机会 | 算法 + 系统 + 一学期真实对比 | 良好 |
| 只拿到规则说明 + 问卷模板 | 算法 + 系统 + 高保真仿真 | 合格 |
| 什么都没拿到 | 算法 + 系统 + 通用仿真 + 完整落地材料 | 合格 |

> **关键：最差情形下项目依然完整。** 因为 §3 的三项创新点都不依赖真实数据 —— 这正是本项目在数据不确定下最大的保险。

### 11.3 让学校真"用起来"的路径

| 级别 | 内容 | 现实性 |
|---|---|---|
| **1 级：看见** | 演示 + 影子运行对比报告："我们的结果比现行方案好 X%" | **9 个月内可做到** |
| 2 级：试点 | 一个学院/一栋楼使用，人工复核后再发 | 加分项 |
| 3 级：替代 | 全量使用 | **不写进承诺** |

### 11.4 隐私合规（谈数据时对方必问，先备好）

- 数据脱敏：学号 → 内部 ID，姓名不进模型输入
- **本地部署、不出校、不联网**
- 用途限定：只用于本项目研究，结项后销毁或交还
- 学生问卷用于研究需告知；涉及发表走学校伦理审查（如有）
- 落成《**数据使用与隐私保护方案**》，**签在协议里**，不做口头承诺

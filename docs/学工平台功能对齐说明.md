> 目的：把本项目（NEST / 学工平台）的功能面**逐条对齐**厦门大学嘉庚学院真实发布的学工业务，而不是自己设想功能。

## 3. P10 spec：勤工助学（逐条来自 S3）

> 出处：[勤工助学管理办法（2021年）](https://xszz.xujc.com/2021/0428/c5069a129069/page.htm)。下列条目括注办法原文条号。

**岗位（第十六~十九条）**
- 类型：`fixed` 固定岗位（持续用工 ≥ 1 学期，有相对固定工时）/ `temporary` 临时岗位（一次性或几次完成）。〔第十七条〕
- 工时上限：**每周 ≤ 8 小时，每月 ≤ 40 小时**（寒暑假可延长）。〔第十六条〕
- 设岗：固定岗位**每学期期末**由用工单位向学生资助管理中心申报；临时岗位**提前 1 周**申报；用工单位不得擅自设置或变更岗位。〔第十八条〕
- 申报内容：岗位工作内容、技能要求、用工时间、用工数量。〔第十八条〕
- 不得把学生干部岗、青年志愿者活动设为勤工助学岗位。〔第十九条〕

**招募与申请（第二十~二十二条）**
- 招募公告须写明：岗位名称、招聘人数、招聘条件、工作内容、劳务报酬、劳动时间、面试时间。〔第二十条〕
- 申请资格：全日制在校生；**同等条件下优先家庭经济困难学生**；**同一学生同一学期原则上不能同时兼任两个及以上固定岗位**。〔第二十一条〕
- 录用：用工单位组织面试、考核 → 签署意见 → 报资助中心备案 → 中心审批、登记、汇总 → 建立学生勤工助学档案。〔第二十二条〕

**计酬、考核与发放（第二十三~二十四条）**
- 按**小时**计酬；临时岗位时薪原则上**不低于 15 元/小时**；固定岗位时薪不低于当地非全日制用工小时最低工资标准。〔第二十三条〕
- 每月发放一次：用工单位**记录用工时间 + 工作考核** → 填《学生勤工助学工作考核表》 → 固定岗每月报送、临时岗活动结束后次月报送 → 资助中心汇总编制**月酬金发放表** → 发放到学校统一办理的银行卡。〔第二十四条〕

**终止（第二十五条）**：① 违纪违法；② 责任心不强/不遵守岗位要求；③ 健康或特殊原因不适合；④ 未如实上报家庭经济条件等失信；⑤ 严重影响学业。终止后停发酬劳并另行招募。

**校外勤工助学（第二十六~二十八条）**：用工单位先向资助中心申请（法人证书副本+证明）→ 中心审核同意并推荐学生 → **学校、用人单位、学生三方签订协议** → 方可开展；酬金不低于当地最低工资。

**其他**：考试周原则上不安排；固定岗聘用期原则上以一学期为限，续聘须重新申请；学生无法到岗须向用工单位请假，辞职须**书面提前 7 个工作日**申请并经用工单位签署意见后报中心。〔第二十九~三十一条〕

**落到本项目的实现口径（推定，字段名自定）**
- 表：`workstudy_post`（岗位：类型/用工单位/名称/内容/技能要求/招聘人数/时薪/工时上限/学期/报名截止/面试时间/状态）、`workstudy_application`（申请：学生/岗位/申请理由/是否困难生/面试结论/录用状态/备案人/时间）、`workstudy_timesheet`（工时：学生/岗位/日期/小时数/工作内容/用工单位确认）、`workstudy_payroll`（月酬金：学生/岗位/月份/总工时/时薪/金额/考核结果/审核状态/发放状态）。
- 校验：同学生同学期固定岗 ≤ 1（服务端硬校验）；单月工时 > 40 或单周 > 8 给出预警（不硬拦，因为办法允许寒暑假延长）；时薪低于下限给出提示。
- 角色：学生申请与查工时；用工单位（=teacher）设岗/面试/记工时/考核；资助中心（=admin）审批岗位、汇总酬金、确认发放。

## 4. P11 spec：困难认定（逐条来自 S4）

> 出处：[家庭经济困难学生认定工作实施的意见](https://xgb.xujc.com/2016/0614/c1985a31287/page.htm)。

- **级别只有两档**：`特困` / `贫困`（现系统用的「一般困难/困难/特别困难」需对齐）。（四·二）
- **认定机构四层**：资助工作领导小组 → 学生资助管理中心 → 院系认定工作组（组长=院长/系主任）→ **民主评议小组**（组长=院系资助工作负责人，成员含班委、团支书、舍友等）。（三）
- **程序七步**：① 学年末发布通知 → ② 学生申请（家庭情况调查表 + 认定申请表 + 民主评议表 + 民政部门盖章证明）→ ③ **民主评议**（现场会议、逐条评议、填民主评议表、写明结论依据）→ ④ 院系认定工作组审核并填认定意见 → ⑤ **班级范围内公示 5 个工作日**（公示姓名、性别、贫困级别；**不得涉及**身份证号、家庭成员信息、收入）→ ⑥ 异议可在公示期内**提请复议**，工作组 **5 个工作日内答复**，属实则调整、并可考虑取消该生资格 → ⑦ 院系提交书面**评审报告** → 资助中心审核 → 领导小组审批定级 → 材料入档。（五）
- **十类不能认定**（已获资助的取消资格、必要时追回）：高档通讯工具、昂贵电脑、奢侈品、经常旅游、校外租房/高档场所消费、因建房购车投资欠巨债、家庭经济已改善、休学/保留入学资格期间、**谎报**、其他不符合条件。（四·三）
- **时间**：每年 9 月认定，结果**有效期当学年**；突发情况可临时受理。**每学期复查一次**，并不定期随机抽选核实。（五·一 / 六·二）
- **动态调整**：学期中可调整（见 S5 公示件标题「认定动态调整」）。

**落到本项目的实现口径（推定）**
- `aid_application` 增：`level` 用 `特困/贫困`、`reviewStage`（`apply/review/committee/publicity/objection/center/leader/approved/rejected`）、`publicityStart/publicityEnd/objectionDeadline`、`committeeNote`（民主评议记录）、`reportNote`（评审报告）。
- 新增 `aid_objection`（复议：申请人/异议人/内容/证据/受理时间/答复时间/结论）。
- 公示页对学生匿名展示（只露姓名+级别），管理员侧露出证据链。

**自动核验（只用库里真实存在的数据，绝不算假）**——`GET /api/honor/my/check?batchId=` 返回逐条条件与来源：

| 条件（通知原文） | 本平台能否自动核验 | 数据来源 |
|---|---|---|

## 8. P13 spec：综测排名公示与导出（逐条来自 S15 与学校办法）

### 8.1 一手事实（2026-10-16 抓取，`page.htm` 全文可抓）

- **《厦门大学嘉庚学院优秀学生奖学金综合测评实施办法（2022年修订）》**，<https://xgb.xujc.com/2022/0823/c1985a139249/page.htm>（学工部·规章制度·校内规章，2022-08-23，浏览量 4.2 万）：
  - **第三条**：测评「采取定量测评与定性评价相结合、结果评定与过程测评相结合、**记实测评与民主评议相结合**的方法，按照**学生个人申报、组织审核、信息化计算评定**的流程开展」⇒ 平台定位就是这套「信息化计算评定」。
  - **第五条**：测评区间「**除毕业学年外，奖学金综合测评以学期为单位进行评定**，一般在下学期开学初完成」。
  - **第六条**：测评对象「依据本办法**以专业为单位进行测评**；转专业的学生，归入测评区间该生所在专业参与测评」⇒ **排名的统计单位是专业，不是班级**。
  - **第十条**：综合测评分数 **M = A + B**（A＝学习成绩测评总得分，B＝综合素质测评总得分）；「**毕业学年第二学期**进行的奖学金综合测评按照往年所有学期的学习成绩测评得分进行排名，**综合素质表现得分不计入**」。
  - **第十一条**：A 由学分加权得出（`a = Σ(ai·ci) / Σci`）；**必修课程与选修课程分别计算**；选修课成绩**二次调整**——「以 80 分为基准，将该原始课程分数与所修选修课程平均成绩的比例作为调整系数」（示例：课程班平均 81.4 ⇒ 系数 80/81.4=0.98，原始分 × 系数）。
  - **第十二条**：**B = C × μ**，其中 C＝学生综合素质表现得分（**奖励加分 − 惩处扣分**，标准见《厦门大学嘉庚学院学生综合素质表现评分参考细则》）；**μ = (H − L) / n**，H＝所在**专业年级**学习成绩测评总得分最高分、L＝最低分、n＝专业年级总人数；「**μ 值设定区间为 0.5–0.7**，凡计算数值大于 0.7 的取值 0.7，小于 0.5 的取值 0.5」。
  - **第七条**：对综合测评**排名前 30%** 的学生给予优秀学生奖学金；**一等奖 1500 元/人·学期、占所在年级的专业人数 5%；二等奖 1000 元、10%；三等奖 500 元、15%**；「各院系奖学金获奖人数严格按照**专业人数乘以获奖比例四舍五入**计算」。
  - **第八条**：分工——「**学习成绩测评由教务部、IT 服务中心负责，综合素质测评由学工部、团委负责**」；院系工作小组由院系主管、学生工作负责人、团委书记、辅导员组成。
  - **第四条**：测评结果作为评选各类奖学金、荣誉称号、推优入党、就业推荐、「第二课堂成绩单」的**主要参考依据**（⇒ 排名是公共基础数据，后面 P12 那类评选要引用它）。
- **《关于2021-2022学年第二学期学生综合素质测评的公示》**，<https://xgb.xujc.com/2022/0905/c1962a139465/page.htm>（2022-09-05，全文）：流程原文＝「经**个人申报、院系审核**，现对…结果进行**公示**，请及时登录**综合教务系统**查看，**有异议者请在公示期内向相应院系辅导员反馈**」；**公示时间 2022 年 9 月 5 日–9 日（5 天）**。

### 8.2 实现口径（**推定部分已逐条标注**）

**与已有模块的关系（重要边界）**：P6 的 `eval_indicator`/`eval_score`/`eval_summary`（德智体美劳五维加权，0–100 分）**保留为「民主评议 / 记实测评」的过程材料**，它**不是**办法里的 C（办法的 C 是加分制，量纲完全不同）。本阶段新增的排名引擎**只认** A（导入）+ C（加分申报审核）+ μ（A 的分布），页面上并列展示五维明细作为佐证，**不拿五维分冒充 C**。

**数据模型（5 张表，`sql\nest_rank.sql`，幂等、带 `SHOW COLUMNS` 自检段）**

| 表 | 作用 | 关键列 |
|---|---|---|
| `eval_academic` | **学习成绩测评 A 的登记台账**（办法第八条把 A 交给教务部/IT 服务中心，平台只登记，不自己算成绩） | `student_id`、`academic_term`、`required_avg`、`elective_avg`（**已二次调整**后的选修加权）、`total_credits`、`course_count`、`score_a`、`source`（`import`/`manual`）、`imported_by`、`note`；UNIQUE(`student_id`,`academic_term`) |
| `eval_bonus` | **综合素质表现加分/扣分申报**（C 的唯一来源） | `student_id`、`academic_term`、`category`（细则六大类，值域与默认上限见 8.1.1：`academic_competition`≤6 / `nonacademic_competition`≤4 / `research`≤4 / `quality`≤1 / `media`≤4 / `service`≤3 / `penalty`＝惩处扣分不设上限）、`item_name`、`points`（**可为负**＝惩处扣分）、`evidence`、`status`(`draft`/`submitted`/`counselor_approved`/`rejected`)、`reject_reason`、`reviewer_id`、`reviewed_at`；KEY(`student_id`,`academic_term`,`status`) |
| `rank_batch` | 排名批次（一次测评＝一个批次） | `batch_name`、`academic_term`、`graduation_last`（毕业学年第二学期 ⇒ 只按 A）、`mu_min`/`mu_max`（默认 0.5/0.7）、`qualify_pct`(30)、`tier1_pct`/`tier2_pct`/`tier3_pct`(5/10/15)、`publicity_days`(默认 5)、`status`(`draft`/`computed`/`publicity`/`finished`)、`notice_title`/`notice_url`、`created_by`、`computed_at` |
| `rank_row` | 计算快照（**每次 compute 全量重写本批次行**，不改别批次；页面展示中间量） | `batch_id`、`student_id`、`major`、`class_name`、`grade`、`score_a`、`c_score`、`mu`、`score_b`、`score_m`、`rank_in_major`、`rank_in_grade_major`、`total_in_major`、`award_tier`（`1`/`2`/`3`/NULL）、`qualified`；UNIQUE(`batch_id`,`student_id`) |
| `rank_objection` | 公示期异议（对应「有异议者在公示期内向辅导员反馈」） | `batch_id`、`student_id`、`reason`、`status`(`pending`/`accepted`/`rejected`)、`answer`、`handled_by`、`handled_at`；KEY(`batch_id`,`status`) |

**计算口径（可解释优先：每一步都要能在页面与导出里看到 A / C / μ / B / M）**

1. **A** ＝`eval_academic.score_a`；缺 A 的学生**不参与排名**，并在管理端列「待补数据」清单（**不猜、不补 0**）。
2. **C** ＝该学期 `eval_bonus` 中 `counselor_approved` 的 `points` 之和（奖励加分 − 惩处扣分）；**先按类别封顶**（`nest.rank.bonus.cap.<category>`，默认 6/4/4/1/4/3，`penalty` 不限），**再对总和封顶 8 分**（**出处＝第十二条「C 不得超过 8 分」**）；两处截断都要在 `/my`、`/list` 与导出里标记「已封顶」，让排名可解释。
   补充：综合测评的**参评资格**（第十三条：有不及格 / 毕业学年第二学期往年必修不及格 >1 门 / 总学分 <专业平均应修学分 75% / 未解除处分或受通报批评）在平台里**只作提示、不硬拦**——底表没有成绩明细与处分数据，硬拦会误伤。
3. **μ** ＝(H−L)/n，H/L 取**同专业同年级**已录 A 的最高/最低分，n＝该专业年级已录 A 的人数；钳制在 `[mu_min, mu_max]`（默认 0.5–0.7，**出处＝办法第十二条**）。同一专业年级只有 1 人 ⇒ n=1、μ 取下限（**推定**：办法未规定，写进页面说明）。
4. **B** ＝C × μ；`graduation_last=true` 的批次 **B=0、M=A**（**出处＝办法第十条**）。
5. **M** ＝A + B，`HALF_UP` 保留 2 位；排名按**专业**（**出处＝第六条**）用 M 降序，**同分并列**（`RANK()` 语义 1,2,2,4 —— **推定**，办法未写并列规则）；另算 `rank_in_grade_major` 供学院与学工部看。
6. **奖学金**：`qualified` ＝ 排名 ≤ 专业人数 × `qualify_pct`（30%，四舍五入）；名额数 ＝ **年级的专业人数** × 5%/10%/15%（各自四舍五入），从第 1 名起按 M 降序依次落位，名额用尽即 `award_tier=NULL`（**名额与等级的落位规则是推定**，办法只给了比例与四舍五入）。
7. **公示**：`publicize` 把批次 CAS 推进到 `publicity`，`publicity_end` 按**工作日**折算（沿用 P11 `AidReviewService.addWorkingDays` 口径与 P12 `publicity_days` 默认 5 —— **出处＝上面那份 5 天公示实例**）；公示接口**必须登录**且脱敏（姓名 / 学号后四位 / 专业 / 班级 / 等级）；异议在公示期内可提，由**该生辅导员**处理（**出处＝公示原文「向相应院系辅导员反馈」**）。
8. **导出**：CSV 带 UTF-8 BOM，表头含 A/C/μ/B/M/排名/等级，admin 与 teacher 可用（「名单以平台导出为准」的先例见 P12 通知）。

**路由（`controller\RankController.java`，`/api/rank/**`）**

- 批次（admin）：`GET /batches`（登录可读、非 admin 自动隐藏 draft）、`POST /batches`、`PUT /batches`（增量）、`POST /batches/{id}/compute`、`POST /batches/{id}/publicize`、`POST /batches/{id}/finish`。
- 学习成绩：`PUT /academic`（admin/teacher，单条登记或修正）、`POST /academic/import`（CSV 文本批量，返回逐行结果）、`GET /academic/missing?batchId=`（待补数据清单）。
- 加分申报：`GET /bonus/my`、`POST /bonus`、`PUT /bonus/{id}`、`POST /bonus/{id}/withdraw`（学生，仅 draft/submitted/rejected 可改）、`GET /bonus/list`（teacher/admin，按学期/状态/关键词）、`POST /bonus/{id}/review`（`{verdict, comment}`，辅导员只能审名下学生；C 只统计 `counselor_approved`）。
- 排名：`GET /list?batchId=&major=&className=&keyword=&page=&size=`（teacher/admin，返回 `{list,total,page,size}` 且**每行都带 A/C/μ/B/M 中间量**）、`GET /detail/{studentId}?batchId=`、`GET /my?term=`（学生看自己的明细与排名）、`GET /publicity?batchId=`（登录必需、脱敏）、`GET /stats?batchId=`（等级/专业分布与待补数据计数）。
- 异议：`POST /objections`（学生，仅公示期内）、`GET /objections/my`、`GET /objections?batchId=&status=`（teacher/admin）、`POST /objections/{id}/handle`（`{verdict, answer}`，该生辅导员或 admin）。
- 导出：`GET /export?batchId=`（CSV + BOM，admin/teacher）。

**页面（2 页，入口全在页内）**：`ranking.html`（学生端：我的 A/C/μ/B/M 拆分解释 + 专业排名与奖学金资格 + 加分申报 + 公示名单 + 异议提交）、`ranking-review.html`（管理端：批次管理 + A 登记/CSV 导入 + 待补数据 + 加分审核 + 一键计算 + 排名表（含中间量列）+ 等级名单 + 公示管理 + 导出 + 统计）。

**验收（每模块独立）**：单测覆盖 μ 的钳制与单人数退化、M=A+B 与 `graduation_last` 特例、同分并列名次、名额四舍五入与落位、C 的封顶、权限矩阵（学生只看自己、辅导员只看名下、跨辅导员 403、admin 全量）；E2E 覆盖「一批次·三学生·导入 A → 申报加分 → 审核 → 计算 → 排名与等级 → 公示脱敏 → 异议 → 导出 BOM」；五套件 + 静态门禁同 P12。

5. **预约规则照 S16 / S17**：提交预约时校验**提前 ≥ 1 个工作日**（非应激，「提前至少一个工作日」；1 个工作日内提交则 400 并提示「如有紧急情况请直接电话联系 0596-6288525」）；接受预约时段**周一至周五 8:00-17:00**；线上咨询走「**提前半天确认**」→ `requested → confirmed`（确认时间距开始不足 12 小时只提示不拦住，因为原文是人工短信环节）；完成时记 `duration_minutes` 默认 **50**；**续约免预约程序** ⇒ `POST /appointments/{id}/renew` 直接沿用**上次的咨询师**生成新预约并写 `renewed_from`（出处＝S17 第五步）。
6. **保密与权限（推定，且不外扩角色）**：学生**只能看自己**（任务 / 结果 / 预约）；`psyche_focus` 与 `psyche_referral` 仅 `admin` 与该生的 `student_profile.counselor_id` 指向的辅导员可见可写（沿用 P3「`teacher`＝辅导员、不新增角色」的口径，心理中心视作 admin 侧）；**列表默认脱敏**（姓名打码、学号只留后四位），全名只在有权限的 detail 里；导出 CSV 需 admin/teacher 且**不含咨询问题全文**；所有读写写审计（`AuditLogService` 新增 `TYPE_PSYCHE="PSYCHE"` 与 `/api/psyche` 分支）——出处＝S16 的「保密性：对个案资料绝对保密」。
7. **学生端不显示自己的关注等级**：`psyche.html` 不渲染 `result_level` 原文，只给一张「心理服务中心建议你与辅导员或中心联系」的提示卡（决策理由：S16 的**自愿性与保密性**原则下，给学生贴「重点关注」标签会直接压制求助意愿；等级只给有权限的老师看）。
8. **匿名 / 脱敏统计**：`GET /stats` 只回聚合数（批次完成率、各院系完成率、关注等级分布、预约量与完成率），**不回可反查个人的明细**；统计口径与列表同源，避免「列表脱敏、统计能反推」。
9. **页面（2 页）**：`psyche.html`（学生端：我的普查任务与作答 / 我的结果查看 / 心理自助与流程说明〔转载 S16 的预约方式与四条原则〕/ 预约申请与我的预约 / 续约）、`psyche-review.html`（管理端：批次与量表、名单与进度、抽查访谈、关注台账、预约排期与确认、转介登记与跟踪、统计与导出）。
10. **路由（`controller\PsycheController.java`，`/api/psyche/**`，约 26 条）**：批次与量表 7（`GET/POST /instruments`、`GET /batches`、`POST /batches`、`PUT /batches/{id}`、`POST /batches/{id}/publish|close`）；名单与进度 4（`GET /batches/{id}/tasks`、`POST /batches/{id}/tasks/import`（CSV 名单）、`GET /batches/{id}/stats`、`POST /tasks/{id}/interview`）；学生 5（`GET /my`、`GET /tasks/{id}`（取题本）、`POST /tasks/{id}/submit`、`GET /tasks/{id}/result`、`PUT /tasks/{id}/result`（中心/辅导员回填））；关注台账 4（`GET /focus`、`POST /focus`、`PUT /focus/{id}`、`POST /focus/{id}/followups`）；预约 7（`POST /appointments`、`GET /appointments/my`、`GET /appointments`、`POST /appointments/{id}/confirm|complete|cancel|renew`）；转介 3（`GET /referrals`、`POST /referrals`、`PUT /referrals/{id}`）；导出 1（`GET /export?type=tasks|focus|appointments`，CSV + BOM，脱敏）；统计 1（`GET /stats`）——(推定：路由形状与 P10–P13 保持一致：成功 HTTP 200 + `{code,message,data}`，状态变更 CAS)。
11. **验收（每模块独立）**：E2E 覆盖「一批次·五学生 → 名单导入 → 学生作答（**未答完被拦**、窗口外被拦）→ 结果回填 → 抽查访谈标记 → 关注台账（含跟进）→ 预约（**提前不足 1 个工作日被拦**）→ 中心确认 → 完成（50 分钟）→ 续约 → 转介 → 脱敏统计 → 导出 BOM」；外加权限用例（跨辅导员 403、学生访问他人任务 403、未登录 401）与「学生端看不到等级原文」的断言；单测覆盖分档阈值、工作日/时间窗校验、预约提前量、续约留痕、脱敏函数；五套件 + 静态门禁同 P12/P13。

- 第三条：学生**应在校住宿，未经学校批准不得外宿**；第四条：住宿由学校统一安排，按指定园区/楼栋/房间/床位住宿，**未经批准不得调换**；第五条：按期足额缴纳住宿费；**第六条：各宿舍应确定宿舍长一名**，宿舍长负责本宿舍管理。

- **第八条（来访）**：来访接待时间 **8:00-13:00 及 14:00-21:30**；须出示证件、登记批准后由被访者带入；**校外男性人员原则上不得进入女生园区**；「在校学生未经学校允许，不得进入异性宿舍，**不得以任何理由留宿非本宿舍人员**」；携贵重物品出园区须登记查验。
- 第九条（健康生活）：禁喧哗起哄、抽烟酗酒打麻将赌博、色情淫秽、迷信邪教、宗教活动、吹拉弹唱与音响跳舞、**饲养宠物及带入园区**。
- **第十条（消防）**：严禁私自接拉电线/改用线路；严禁电热器、电炊具、大功率电器；严禁为电动车（含滑板车/平衡车）及其电池充电、严禁从楼内拉线到楼外充电；不得烧菜煮饭、燃放烟花爆竹与孔明灯、使用明火；不得存放易燃易爆与有毒有害物品；不得擅自使用/移动/拆装消防设施；**不得在走廊、楼梯口等消防通道摆放物品**。
- 第十一~十四条：人财物安全防范（阳台护墙/窗台不得摆花盆等杂物）；公用财产保全（不得拆卸搬出家具、不得拆改水表电表淋浴器、不得张贴涂写刻画）；网络安全（**不得使用路由器连接校园网**）；**传染病报告**（宿舍内有患者或疑似患者应及时报告辅导员）。
- 第十五条：水电计费——**免费额度内不收费，超出自费**。第十六条：统筹宿舍管理——不得私自调换、**不得出借/出租床位**、不得占用空置宿舍与园区功能场所；调整宿舍须上交钥匙。
- **第十七条（卫生检查与文明宿舍，P15 的核心口径）**：「宿舍内务与卫生要求整齐、清洁和安全，宿舍垃圾实行袋装化……**校大学生自律委员会和各院系定期组织对宿舍内务进行检查和评分，并及时在全校公布**；**学校每学期开展一次校级「文明宿舍」评比活动**。」
- 第十八条：园区禁商业行为（推销、兜售、张贴广告、投放宣传单），**外卖送餐人员不得进入园区**。第十九~二十条：退宿（外宿/休学/毕业/转学/退学等应搬离并办退宿手续；**未办退宿手续的学生离校期间仍须交纳住宿费**）。第二十二条：寒暑假**留校学生集中住宿**，其余园区封闭管理；**第二十四条：学校不定期开展园区安全检查工作**；第二十五条：违反本规定按《学生违纪处分管理规定》处理，造成设施遗失或损坏应恢复原状或照价赔偿。

**S20《厦门大学嘉庚学院学生违纪处分管理规定（2025年修订）》**（2025-06-24，<https://xgb.xujc.com/2025/0624/c1985a160723/page.htm>，全文可抓）

- **第四十一条（园区违规，P15 的处理依据）**：「违反学校学生园区管理规定，在园区有下列情形之一的，**视情节轻重，给予警告以上处分**」——（一）未经批准**晚归、夜不归宿**或未履行手续在校外租房居住；（二）留宿他人或在他人宿舍留宿；（三）违规占用床位或妨碍他人入住；（四）出租、出借、转让宿舍床位；（五）使用明火或焚烧物品；（六）攀爬墙壁、破坏门禁、暴力拉门等非正常方式进入园区；（七）高空抛物或引发高空坠物隐患；（八）违章接拉电线；（九）使用电热器、电炊具、大功率电器等；（十）饲养、容留宠物或带入园区；（十一）从事或协助营利性活动扰乱宿舍区秩序；（十二）违反作息制度扰乱他人正常生活秩序；（十三）其他违反园区管理规定行为。
- **第四十二条（消防）**：（三）占用公共消防通道、堵塞安全出口 → 警告以上；（四）在宿舍区等为电动车辆及其电池充电或从楼内拉线到楼外充电 → 警告以上；（五）过失引起火情火灾 → 严重警告以上，因违规用火用电引起 → 记过以上。
- **第六十三~六十九条（处分程序，P15 只登记不替代它）**：院系学生工作组调查核对事实、收集现场证据、听取学生（或其法定代理人）陈述申辩，**10 个工作日内**提出初步处理意见并送学工部；材料含调查报告与处分意见、询问笔录或陈述材料、其他证据，询问须 2 名以上工作人员在场；告知事实理由依据与陈述申辩权，异议可在拟处理意见通知书送达之日起 **7 日内**提出；处分决定书 **10 个工作日内**送交本人签收；拒收可留置送达（2 名以上见证人）；**公告送达 15 日**视为送达；异议依《学生申诉办法》申诉；处分与解除材料归档。

> **无从考证（明确不猜）**：学校宿舍**卫生/安全检查评分表的评分项与权重**（公开出处只有「定期组织对宿舍内务进行检查和评分」，没有评分表正文与分值）；检查**频次**（原文只写「定期」「不定期」）；**文明宿舍名额与比例**；园区**门禁刷卡数据的接口与字段**（平台没有门禁硬件）；社区管理在学工平台 `ijg.xujc.com` 内部的菜单与字段。

### 11.2 实现口径（**推定部分已逐条标注**）

1. **平台不做「自动资格判定」**（推定）：阶段推进由支部书记/辅导员手工操作，平台只做「**台账 + 时限提醒 + 公示留痕 + 材料清单**」；所有「应当/不得」显示为**带条款引用的提示文案**（`rule_ref`，如「S23 第二条：两个月以上」），不阻断推进。
2. **数据模型（7 张表，前缀 `party_`）**：`party_application`（入党申请登记：申请时间/谈话时间/谈话人/党支部）、`party_stage`（阶段台账：`applicant→activist→candidate→probationary→full`，每步发生日期 + 该步公示起止 + 依据说明）、`party_observation`（考察与思想汇报台账：`thought_report` / `observation`，提交时间/内容/审核人/审核时间）、`party_training`（党校班次）、`party_training_member`（学员报名与结业：状态、结业日期、证书编号、有效期至）、`party_publicity`（公示：节点类型/起止/工作日数/异议入口/结论）、`party_material`（材料清单：材料名/应交阶段/已交与否/备注）。学生与支部的关联沿用 `student_profile.counselor_id`，支部信息落在 `party_stage.branch_name`（不新建支部主数据表；支部主数据未获来源）。
3. **期限常量（全部来自 11.1 原文，可在页面上显示来源）**：申请后 **1 个月**内谈话；确定积极分子前需**党支部 2 个月以上**培养教育；积极分子→发展对象需**1 年以上**培养教育和考察；入党积极分子考察**每半年一次**（同时保留校内「每季度考察」表述，两条都标注来源）；党校培训**不少于 3 天 / 24 学时**（国标）或**5-7 天 / 不少于 40 学时**（校规）—— 两条并存、页面标注出处，**平台不替学校选**；预备期 **1 年**，延长一次 6–12 个月；上级审批 3 个月内（最长 6 个月）；公示 **5 个工作日**（校规 5-7 天）；思想汇报**至少每季度**，超 **3 个月**未交提示「可能取消积极分子资格」；再次确定为积极分子原则上 **2 年**内不得。

### 13.1 一手事实（2026-10-16 采集；逐字摘录缓存 `target\p18-sources.md`）

- **S26（部级文件，转载非一手）**：共青团中央《关于在高校实施共青团「第二课堂成绩单」制度的意见》（**中青联发〔2018〕5 号**）。已核对文本给出的制度框架只有四件事：
  ① **七个内容板块**（可配置）；② 计量可采「**学分式评价**」，即学时与学分两种口径都要能表达；③ **四级记录流程**「学生申报 → 团支部/院系审查 → 主办方审核 → 校团委认定」；④ 与**综测 / 评奖评优 / 推优**挂钩。
- **S26 没有任何数值**：每板块要求多少学时、学时怎么折学分、单学年上限多少 —— 部级文件不规定，**一律由学校自定**。⇒ 本模块所有阈值都是可配置字段，**建表不预置任何数字**，NULL 的语义就是「学校还没定」，页面必须显示「未设置」而不是 0。
- **S26 未在可引用文本中给出七个板块的完整名称** ⇒ 仓库里出现的板块名（思想成长 / 实践实习 / 志愿公益 / 创新创业 / 文体活动 / 工作履历 / 技能特长）只存在于演示数据 `sql\nest_secondclass_demo.sql`，**不是引自文件**，生产库不预置任何板块。
- **S27（官方栏目，`https://xgb.xujc.com/czsc/list.htm`）**：成长手册栏目仅 **6 篇**（菁菁嘉园 / 安全至上 / 大学规划 / 红色警戒线 / 读书之乐 / 给心灵洗洗澡），**全文无「第二课堂」「学分」「学时」字样** ⇒ 校内**是否已实施**第二课堂制度**未能核实**（`docs\学工平台功能对齐说明.md`:39 原记录）。
- **制度事实边界**：S26 的四级流程里，「团支部/院系」与「主办方」在学校的系统里**都没有独立账号体系**（P16 党建台账已实测：团支部没有独立登录主体），因此本模块**不假装四级**。

### 13.2 实现口径（**推定部分已逐条标注**）

1. **平台不替学校定口径（推定，最重要的一条）**：板块的 `required_hours`（要求学时）、`yearly_cap_hours`（单学年计入上限）、`credit_per_hour`（学时→学分换算系数）**全部可为 NULL**，NULL 原样下发给页面并渲染成「未设置」；`yearly_cap_hours` **不硬截断**，只在汇总里给出「计入上限」与「超出多少」由认定人判断（避免系统替学校改数）。
2. **诚实声明（页面与文档统一）**：校内是否已实施第二课堂制度**待学校确认**；本模块按 S26 的制度框架做成**板块与换算全部可配置**——学校试点时先建板块、再设学时与学分口径，系统不自带任何默认值。
3. **数据模型（3 张表，`sql\nest_secondclass.sql`）**：`second_class_category`（板块：名称 / 短码 `uk_category_code` / 展示序 / 要求学时 / 学年上限 / 学分系数 / 口径说明 / 启用位 / 软删）、`second_class_activity`（活动库：板块 / 名称 / 主办单位 / 级别 `school`/`college`/`class`/`other` / 起止日期 / 申报学时 / 可折学分 / 地点 / 说明 / 状态 `draft`/`published`/`closed`）、`second_class_record`（申报与认定：活动 id〔自报项目为 NULL〕 / 板块 / 学生 / **标题与学时快照** / 佐证材料 / 学生备注 / 状态 / 退回原因 / 初审人与时间 / 认定人与时间 / 软删）。
4. **快照口径（硬）**：`record.title_snapshot` + `record.hours` 在申报时从活动**快照**下来，活动事后改名或改学时**不影响**已申报记录；`uk_record_activity_user(activity_id,user_id)` 保证同一活动同一学生只有一条记录（自报项目 `activity_id` 为 NULL，不受此约束）。
5. **状态机（两级审核，**不假装四级**）**：`submitted` ─辅导员初审通过→ `counselor_approved` ─认定通过→ `confirmed`（终态）；`counselor_approved` ─认定不通过→ `rejected`（终态）；`submitted` ─学生撤回→ `withdrawn`（终态）；`submitted` ─辅导员退回→ `returned` ─学生改后重交→ `submitted`。活动侧：`draft` ─发布→ `published` ─结束→ `closed`。**合并四级为两级的理由**：S26 的「团支部/院系审查」与「主办方审核」在系统里没有独立账号主体，合并为一次「辅导员初审」，认定由 `admin`（代表校团委）做——**合并事实写进页面说明与诚实清单，不虚构四级流水**。
6. **CAS 与终态（硬口径，沿用 P14–P17 教训）**：所有状态变更 `UPDATE ... WHERE id=? AND deleted=0 AND status=#{fromStatus}`，`fromStatus` 取**显式枚举前置态**；影响行数 0 → 业务码 400「状态已变化，请刷新后重试」；终态不可再改。
7. **判定规则**：挂活动申报要求活动 `published` 且无重复申报（重复 → 400「已申报过该活动」）；自报项目要求 `categoryId`+`title`+`hours` 必填、`hours ∈ (0,100]`；板块停用（`enabled=0`）不可新申报但历史记录照常可查；初审 `teacher` 限定在 `student_profile.counselor_id` 名下（沿用 P13 `scopeCounselor`：未分派学生的辅导员按全校），`admin` 可代审；**认定仅 `admin`**且只能从 `counselor_approved` 认定；退回/驳回原因必填（空白 → 400「请填写原因」）；汇总按 `submitted_at` 的自然年统计（**学年口径由学校定，界面注明**）。
8. **权限映射（推定，关键取舍）**：S26 把认定权交给「校团委」→ 平台把**认定**映射给 `admin`（校级），`teacher`（辅导员）承担**初审**与**退回**；学生只看自己并申报/撤回。数据级授权：学生只看自己、教师只看名下学生、`admin` 全量，跨范围 403（文案含「无权」）。
9. **接口（21 条，`/api/second-class`，真实路由见 `target\p18-spec.md` §5）**：学生侧 `GET /categories`、`GET /activities`、`GET /my`、`GET /summary`、`POST /records`、`PUT /records/{id}`、`POST /records/{id}/withdraw`；员工侧 `GET /review`、`GET /review/stats`、`GET /records/{id}`、`POST /records/{id}/counselor-review`、`POST /records/{id}/confirm`、`GET /export`；管理侧 `GET|POST /admin/categories`、`PUT /admin/categories/{id}`、`GET|POST /admin/activities`、`PUT /admin/activities/{id}`、`POST /admin/activities/{id}/status`；另有 `GET /health`。全部 HTTP 200 + `{code,message,data}`；导出是唯一例外（`ResponseEntity<byte[]>`，越权时非 200 且空 body，与 P17 两模块同口径）。
10. **导出脱敏**：CSV 带 UTF-8 BOM、`text/csv; charset=UTF-8`、文件名 `second-class-<yyyyMMdd>.csv`；教师只导名下学生、`admin` 导全部；**不含**学号全量与联系方式。
11. **与既有模块的边界（推定）**：P17 志愿服务的学时与第二课堂「志愿公益」板块是**两套台账**（P17 记服务时长与星级，P18 记申报认定），**不自动把 P17 时长并入 P18**（口径不同，自动折算等于替学校定规则）；综测（P13）与评优（P12）只读 P18 的 `confirmed` 结果即可对接，本轮**不写自动同步**。
12. **诚实清单（本轮不落地 / 未核实）**：① 校内是否实施第二课堂制度**未核实**（S27 无任何字样），系统只提供可配置能力；② 七个板块的完整名称与各板块学时要求**无来源**，演示数据之外生产库不预置；③ 学时→学分的换算系数**无来源**，NULL = 未设置；④ 「学分式评价」的具体认定办法**无原文**；⑤ 与综测/评优/推优的**挂钩规则**不做自动计算，只留 `confirmed` 状态与汇总接口；⑥ 系统**不产出**官方《第二课堂成绩单》证书版式（无来源）；⑦ 通知渠道（短信/邮件）不存在，退回与驳回只落库并由页面/站内可见。

## 14. 质量硬项记录：权限矩阵与数据级授权（P0-3，2026-10-19，**非功能项**）

这一节不描述新业务，只记录「谁能调哪个接口、按 id 直取时谁算有权」的可复查结论，因为**框架层不做兜底**：
`src/main/java/com/umi/nest/config/SecurityConfig.java:35-44` 的 `.requestMatchers("/api/**").permitAll()`
决定了一切授权都靠手写守卫，漏一条就敞开。

**怎么复查（不需要读代码）**：`node tools\authz-audit.mjs` → 22 个控制器 / **151 条路由**四张表
（控制器 × 路由 × 守卫落点 / 控制器内既不判也不调服务的 / 按 id 直取的 `GET` 归属落点 / 服务层闸门计数），
明细 `target\authz-matrix.json`；结论与判读写在 `docs\权限与数据级授权审计.md`。

**三条判读结论（值得记住）**：

1. **`/api/auth/register` 公开是安全的**：角色不由客户端决定——无邀请码 → `student`，有邀请码 → 校验库内码
   （过期/次数用尽）或配置码 → `teacher`，密码另过 `PasswordPolicy.check`。**不构成提权入口**。
2. **18 条按 id 直取的读接口里，17 条的归属判断在服务层**（本人 / 名下学生 / 同宿舍 / 管理员，拒绝时中文
   「无权…」+ 403）；只有社团详情与公示是「登录即可见」，属公示业务的**设计选择**，不是漏做。
3. **框架层仍是 `permitAll`**：过等保测评前必须补一层粗筛——但**不能直接加 `hasAnyRole`**：这套代码
   只注册了 `BCryptPasswordEncoder`，全仓库没有 `UserDetailsService`/`SecurityContextHolder`，框架眼里
   所有人都是匿名，`.hasAnyRole("ADMIN")` 的结果是「谁都进不去」。正确形态是 `HandlerInterceptor`
   （本仓库已有 `DormStaffInterceptor` 先例）。这条**没做**，写在这里防止被误读成「权限已经体系化」。

**同期的真机复核**：静态读代码只能看「有没有调守卫」，所以又补了一层真机三身份矩阵
`node tools\authz-live.mjs`（读 151 条路由，匿名 / 学生 / 教师各打一遍）——**149 条参与实测、VERDICT OK**：
匿名 141/141 被拒（白名单 8 条可用）、学生打 63 条员工路由 0 放行、教师打 12 条管理路由 12/12 被拒。

**同期修掉的两个真缺陷**：

1. `GET /api/user/avatar/file/{filename}` 原先不要求登录、文件名零校验，Windows 下 `\` 与 `/` 同为分隔符
   ⇒ `..\..\application.properties`（含数据库口令）可被匿名读出。现为「登录 + 文件名白名单
   `^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$` + 目录前缀兜底」三层；12 个单测 + 12 条真机断言在案。
2. `POST /api/user/avatar` 在未登录或非 multipart 请求下会吐 HTTP 500（`@RequestParam("file") MultipartFile`
   在参数解析阶段就抛，登录判断没跑到）——这不是越权，但会让值班的人误判成服务故障；改为
   `required = false` 后，未登录回「未登录」、没带文件回「请选择要上传的文件」。

改完复跑：`mvn "-Dtest=UserControllerTest,UserServiceAvatarFileTest" test` **35 / 0**、
`node tools\e2e-p18.mjs` 仍 **304 / 0**、全量 `mvn test` **1,577 / 0**。

**框架层角色粗筛（2026-10-20 追加）**：§14 当时把「框架层兜底」列为没做，这一轮补了粗筛的一半 ——
`ApiRoleGuardInterceptor` + `ApiRoleGuardConfig` 挂在 `/api/**`，24 条规则（P19 又补 2 条：`/api/loan/review/**`、`/api/loan/export`）：`/api/admin/**` 只放 `admin`

`batches`、`/api/counselor/**`、`/api/eval/compute`、`/api/loan/review/**` 等）只放 `admin` + `teacher`。
**有意不覆盖**学生也在用的双用途路径（`/api/honor/batches`、`/api/rank/batches`、
`/api/community/inspections/{id}`、`/api/community/activities/*/signup`、`/api/club/reviews`），
它们的「是不是你的」是数据级判断，只能留在服务层 —— 边界与理由在 `docs\权限与数据级授权审计.md` §7.1。

## 15. P19 spec：生源地信用助学贷款登记（来源 S6，**字段口径为学校自定**）

### 15.1 一手事实（可引用的只有一句）

`docs\学工平台功能对齐说明.md:18` 记 S6（学校学生资助网）栏目包含「生源地贷款」；
`:51` 记当年差距为「回执 / 贷款信息登记（合同号、金额、到账确认）**缺失**」。
这两条只能支撑「学校资助业务里确实有生源地贷款这件事、且需要在系统里登记」，**支撑不了任何字段表**：
一手页面上没有写合同号格式、没有写金额区间、没有写生源地要到哪一级行政区、没有写回执校验码是否必填、
也没有写谁能核验。因此本模块的字段与校验一律按下面 15.2 的「学校自定」口径实现，不冒用任何政策文本里的数字。

### 15.2 实现口径（12 条）

1. **表**：`sql\nest_loan.sql` 一张 `student_loan`，24 列，4 个二级索引（`user_id+academic_year` / `status` / `counselor_id` / `academic_year`）。
   `disbursed` 是 `TINYINT` + `disbursed_at DATE`，表示「学生自己在系统里标记已到账」，**不是银行回单核验**。
2. **学年格式**：`^\d{4}-\d{4}$` 且后段 = 前段 + 1，年份 2000–2100。写成 `2026/2027` 或 `2026-2028` 一律 400 并说清正确形状。
3. **金额**：`DECIMAL(10,2)`，必须 > 0 且最多两位小数；上限 `AMOUNT_SANITY_MAX = 1000000` 在代码注释里写明是「**防误填上限，不是政策上限**」，
   错误文案同时带「防误填」与「本系统不设政策上限」两句话，避免被当成学校发布的贷款额度。
4. **不做行政区划校验**：省 / 市 / 县三个字段都是自由文本，系统不内置行政区划代码表 —— 内置一份就会立刻过期。
5. **不做经办行白名单**：`bank_name` 自由文本（国开行、农信社、其他商业银行都行），因为学校页面没写经办行范围。
6. **回执校验码可选**：`receipt_no` 允许为空，系统不校验其格式 —— 政策文本里没给出校验规则。
7. **同一学年一条有效登记**：`withdrawn` / `rejected` 不占名额（可以重报），其余四态都算占用，
   重复提交回「本学年已有贷款登记（<状态中文>），不能重复提交」，且把当前状态写进消息里，学生知道卡在哪一步。
8. **状态机两段**：`submitted`（待核验）→ 辅导员 `counselor_approved`（辅导员已核）→ 管理员 `confirmed`（学校已确认）；
   另有 `returned`（退回待改）/ `rejected`（不予登记）/ `withdrawn`（已撤回）。每次转移都是 CAS（`WHERE … status = #{fromStatus}`），
   并发下第二次转移返回「数据已变化，请刷新后重试」而不是静默覆盖。退回与不予登记**必须填原因**。
9. **谁能在哪一步动**：学生只能改 / 撤 / 标到账自己的、且状态在 `submitted` / `returned`（`updateByStudent` 的 WHERE 里就写着）；
   辅导员只能动自己名下学生（`countByCounselor` 口径，与 P13/P18 一致）；**确认只有管理员能点** —— 因为「学校已确认」意味着学校认这笔账，
   不能由辅导员代签。测试钉住了「辅导员调 confirm 得 403」与「`confirmed` 不能再被核验」。
10. **导出**：14 列 CSV，学号只留后 4 位、姓名首字 + `*`（复用 `CommunityService.maskName` / `tail4`），
    5000 行上限，文件名 `student-loan-<yyyyMMdd>.csv`，UTF-8 BOM；未登录 / 非员工一律拒绝（粗筛先答 401/403，控制器再拒一次给 403 空 body）。
11. **和助学金的关系**：**两本台账，不自动联动**。`policyNote()` 原文写明「不改变助学金评定结果」——
    学校页面上没有写贷款与助学金的联动规则，系统就不断言。
12. **前端不加新页面**：`static\aid.html` 与 `static\aid-review.html` 各加一个 `border-t` 分隔区块，
    没有动导航、没有动 `check-unify` / `check-redesign` / `page-contract` 的页面计数（48 / 26 / 48 都不变）。

### 15.3 没做 / 做不到（诚实清单）

1. **不做银行或生源地资助中心的对接**：没有接口、没有回执真伪核验，`disbursed` 只是学生自述标记。
2. **不做金额与学校政策的比对**：学校没给出额度口径，系统不判「超没超」。
3. **不做生源地行政区划的结构化统计**：省 / 市 / 县是自由文本，只能按字符串筛。
4. **不做贷款台账与学费缓交 / 绿色通道的联动**：那是另外两条业务线，本轮没碰。
5. **不做历史贷款批量导入**：只有 `POST /api/loan` 单条登记；如果学校有往年数据，需要先给导入模板。
6. **`docs\学工平台改造路线图.md` 里 P19 原记「计划中」**，本轮已改为完成并加 §2.24 落地记录。

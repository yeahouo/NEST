# 权限矩阵与数据级授权审计（P0-3）

> 日期：2026-10-19 ｜ 审计对象：`src/main/java/com/umi/nest/controller` 全部 22 个控制器、**151 条路由**
> 工具：`tools\authz-audit.mjs`（可反复跑）｜ 明细：`target\authz-matrix.json`
> 结论一句话：**框架层没有做鉴权（`/api/**` 全 `permitAll`），授权全靠手写守卫；本轮把「谁在守、守到哪一层」变成 4 张可复查的表，并修掉 1 个真实越权读文件漏洞。**

## 1. 先说清楚现状：三层里原本只有后两层在守（2026-10-20 起补了①的粗筛）

> 本节写的是**审计当时的现状**，保留原文以便对照。随后落地的框架层粗筛见 §7.1：
> 它在①里补了 24 条「路径 → 允许角色」的规则，但①仍未做成完整的 SecurityContext 鉴权。

`src/main/java/com/umi/nest/config/SecurityConfig.java:35-44` 的原文就是结论：

```java
.authorizeHttpRequests(auth -> auth
    .requestMatchers("/", "/index.html", "/login.html", "/register.html").permitAll()
    .requestMatchers("/css/**", "/js/**", "/images/**", "/fonts/**", "/student/**").permitAll()
    .requestMatchers("/student/**", "/teacher/**", "/admin/**").permitAll()
    .requestMatchers("/api/**").permitAll()      // ← 所有接口在框架层是放行的
    .anyRequest().permitAll()
)
```

所以实际生效的是这三层里的**后两层**：

| 层 | 谁负责 | 表现 | 覆盖 |
|---|---|---|---|
| ① 框架层（Spring Security） | `SecurityConfig` + `ApiRoleGuardInterceptor`（§7.1 后补） | 过滤链仍全放行；拦截器按路径表挡 24 条员工/管理员面 | 审计时 0 条 → 现在 24 条规则 |
| ② 控制器层 | 22 个 Controller | `session.getAttribute("userId")` 判登录；角色判断写在服务层 | 151 条都至少有一层 |
| ③ 服务层 | 各 `XxxService` | `guardLogin / guardStaff / guardAdmin / isAdmin / isStaff` + **资源归属**（本人 / 名下学生 / 同宿舍 / 管理员） | 见 §3、§5 |

**这个结构的代价**：只要有人在控制器里忘了把 `actorId` 传进服务、或服务里少一句归属判断，接口就是敞开的，没有任何兜底能拦住。所以「读一遍 22 个控制器」不是可选的——本轮就是把这件事自动化。

## 6. 本轮修掉的缺陷 D1：头像接口路径穿越（真漏洞）

**原实现**（`UserService.loadAvatarFile`）：

```java
Path uploadPath = Paths.get(uploadDir).toAbsolutePath();
Path filePath = uploadPath.resolve(filename).normalize();   // ← filename 未做任何校验
Resource resource = new UrlResource(filePath.toUri());
```

`filename` 来自路径变量，**Windows 上 `\` 与 `/` 都是分隔符**，`..\..\application.properties` 会把上传目录的上级再上级拼进来，命中就能把 `application.properties`（含数据库口令）原样读出去；同时该接口**不要求登录**，等于匿名可枚举。

**修法（三层，缺一层都不够）**：

1. 控制器 `UserController.getAvatarFile(..., HttpSession session)` 要求已登录，匿名 → `403` 空体，且**不调用服务**（单测 `verify(never())` 钉住）。
2. 服务层白名单 `^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$` + 显式拒绝 `..`、`null`、空串 → `403`（**不回默认头像**，避免把「被拒绝」误读成「没头像」）。
3. `filePath.normalize()` 之后再判 `filePath.startsWith(uploadPath)`，作为白名单被放宽时的兜底。

**证据**：

- 单测 `src\test\java\com\umi\nest\service\UserServiceAvatarFileTest.java`：**12 个用例**（10 条路径类输入参数化 + null/空串 + 超长名 + 合法名放行），`mvn -Dtest=UserServiceAvatarFileTest,UserControllerTest test` → **34 / 0**（`target\test-avatar-authz.log`）。
- 真 HTTP 实测 `node target\verify-avatar-authz.mjs` → **12 / 12 全 OK，VERDICT OK**：匿名合法名 403；已登录合法名 200 `image/svg+xml`；反斜杠/正斜杠/双编码/裸点号/盘符绝对路径/超长名 全部非 200 或非图片，且响应体**不含** `spring.datasource`/`jdbc:` 等关键字。
- 实测同时暴露一个事实：编码过的 `%5C`/`%2F` 在 **Tomcat 层就被 400 拒掉**，未编码的 `..\..\` 在 **Spring 路径匹配层 404**，所以真正能到达白名单的输入很少——但白名单仍是必须的第三层（容器配置一变，前两层就可能放行）。

## 6.1 另一处修掉的缺陷 D2：头像上传在未登录 / 非 multipart 时会吐 HTTP 500

真机巡检（见 §9）打 `POST /api/user/avatar` 时拿到的是：

```
http=500  {"code":400,"message":"服务器内部错误: Current request is not a multipart request"}
```

**成因**：方法签名写的是 `@RequestParam("file") MultipartFile file`，Spring 在**参数解析阶段**就要求请求是 multipart，解析失败直接抛异常，`HttpSession` 里的登录判断根本轮不到执行；异常再被全局异常处理器兜成 HTTP 500。

**危害**：不严重（不是越权也不是数据泄露），但它是**错误处理缺陷**——任何客户端（含扫描器、老版本 App）不带 multipart 请求体碰一下这个接口，日志里就会多一条 500，值班的人会当成服务故障去查。

**修法**（一行签名 + 一句注释）：`@RequestParam(value = "file", required = false) MultipartFile file`。于是：

| 请求 | 修前 | 修后 |
|---|---|---|
| 匿名 `POST`（无 multipart） | HTTP 500 | `HTTP 200` + `code 400 未登录` |
| 已登录但没带文件 | HTTP 500 | `code 400 请选择要上传的文件`（`UserService.java:740-742` 原有校验接管） |

单测：`UserControllerTest.UploadAvatarTests` 新增「已登录但没带文件」一条（`post("/api/user/avatar").session(session)` + `uploadAvatar(eq(1L), isNull())` 打桩），整套跑 `mvn "-Dtest=UserControllerTest,UserServiceAvatarFileTest" test` → **35 / 0**（`target\test-avatar-upload-fix.log`）。

## 7. 为什么「框架层兜底」不能直接写 `.hasAnyRole(...)`

这一条必须先说清楚，否则「加个 `.hasAnyRole("ADMIN")` 不就好了」会把整个系统锁死。

- `SecurityConfig.java` 全文 53 行，只做了两件事：注册一个 `BCryptPasswordEncoder`、给了`http.csrf().disable()` + 全 `permitAll` 的过滤链 + `formLogin.disable()` + `logout.disable()`。
- 全仓库 grep `UserDetailsService` / `AuthenticationManager` / `SecurityContextHolder` / `UserDetails` —— **零命中**。

也就是说：**没有 SecurityContext 身份**，Spring Security 眼里所有人都是匿名。此时写 `.hasAnyRole("ADMIN")` 的结果不是「只放管理员」，而是「**谁都进不去**」。

真要补框架层兜底，正确形态是 **HandlerInterceptor**（本仓库已有先例：`DormStaffInterceptor` 就是按会话属性拦 `/api/dorm/**` 的），在 `preHandle` 里读 `session.getAttribute("role")` 做粗筛，细粒度归属仍留在服务层。

## 7.1 已落地的粗筛：`ApiRoleGuardInterceptor`（2026-10-20 补）

§7 的路线在这一轮落成了代码，规模刻意做小：

| 文件 | 作用 |
|---|---|
| `src\main\java\com\umi\nest\config\ApiRoleGuardInterceptor.java` | 规则表 + `preHandle` 判定，24 条规则 |
| `src\main\java\com\umi\nest\config\ApiRoleGuardConfig.java` | 把拦截器挂到 `/api/**`（不写白名单，拦谁由规则表回答） |
| `src\test\java\com\umi\nest\config\ApiRoleGuardInterceptorTest.java` | 10 条单测（含「双用途路径不许碰」） |
| `tools\verify-api-guard.mjs` | 真机验证，30 条断言 |

规则分两档：`/api/admin/**` 只放 `admin`（**前缀匹配**，以后往管理端加接口自动受保护）；其余 21 条是「只有员工页面在调」的面——`/api/counselor/**`、`/api/*/review/**`、`/api/*/export`、`/api/workstudy/manage/**`、`/api/psyche/batches/**`、`/api/second-class/{review,admin}/**`、`/api/eval/compute`、`/api/community/{batches,stats,export,civil-rooms/compute,inspections/import}` 等，只放 `admin` + `teacher`。

**为什么只覆盖这一小片，而不是 151 条**：很多前缀是双用途的，粗筛碰它们就是打断学生端页面。实测证据（静态页调用方统计）：

- `/api/honor/batches`、`/api/rank/batches` —— 学生页 `honor.html` / `ranking.html` 在看可申报批次；
- `/api/community/inspections/{id}` —— 学生要看**本宿舍**的检查结果（归属判断在 `CommunityService.inspectionDetail`）；
- `/api/community/activities` —— 学生报名 `POST /activities/{id}/signup` 与员工创建 `POST /activities` 同前缀；
- `/api/club/reviews` —— 学生评价社团。

对这些面按路径粗筛会把「归属」这件数据级的事错当成「角色」的事，所以**有意留在服务层**。角色能挡的挡在框架层，归属该由服务层判——这条边界写在这里，免得下次有人「顺手补全」。

**配置**（`application.properties` 里可覆盖，默认值就是出厂值）：

```properties
nest.api.admin-roles=admin
nest.api.staff-roles=admin,teacher
```

配置写空时回落到上面的出厂值——失败方向只能是「谁都不许进」，不是「谁都能进」（有单测钉住）。

**响应形态**：HTTP 200 + `code 401/403` 的 JSON，与全站「所有业务响应 200 + 业务码」的约定一致；前端每页都只读 `json.code`（`second-class.html` 里 `result.code === 401` 跳登录就是这个模式）。宿舍管理端那个拦截器回 HTTP 状态码，它守的是另一套只看 HTTP 状态的面，两者不冲突。每次拒绝会打一条 WARN（含方法、路径、角色），上线后回看日志就知道「谁在打哪个面」。

**真机读数**（`tools\verify-api-guard.mjs`，服务 :8080 实跑）：30 / 30 通过 —— 管理端匿名 401 / 学生 403 / 教师 403 / 管理员 200；员工面学生 403、教师 200；10 条双用途路径学生全部**未被粗筛拦**；匿名既有登录闸门未受影响。

## 8. 已知接受风险（写清楚，不装作没有）

1. **框架层只做了粗筛，没有做完整体鉴权**：`/api/**` 在 Spring Security 里仍全 `permitAll`（不能直接加 `.hasAnyRole`，见 §7）。补偿是三层：① `ApiRoleGuardInterceptor` 粗筛 24 条「只有员工/管理员在用」的路径（§7.1，覆盖管理端全部 12 条接口且对新增管理端接口默认拒绝）；② 各服务方法手写的 `guardLogin / guardStaff / guardAdmin`（覆盖归属这类数据级判断）；③ 静态审计（151 条）+ 真机矩阵（149 条）两把尺子。**仍然缺的是**：双用途路径（`/api/honor/batches`、`/api/community/inspections/{id}` 等）的框架层保护，以及「接口按角色整体收口」的等保口径——前者会打断学生端，后者要先有 SecurityContext 身份。
2. **CSRF 关闭**（`SecurityConfig.java:33`）：会话 Cookie 认证 + `csrf.disable()` ⇒ 跨站表单可发起写操作。当前部署为内网单域、无第三方站点嵌入，接受；若接入统一门户/外链，必须补 CSRF token 或 `SameSite=Strict`。
3. **社团详情/公示登录即可见**：全校师生可查任意社团台账与公示，属业务设计（公示本身就要全校可见）。
4. **`/api/second-class/health` 暴露内部路由名**：无调用方，纯自检用，接受。
5. **会话单点**：后登录会把前一个会话顶掉（P15 的记录），不是漏洞但会让人以为「被踢了」——写在这里免得再被当 bug 查一遍。

## 9. 真机三身份矩阵实测（149 条路由）

静态读代码只能证明「控制器里有没有调守卫」，证明不了「跑起来真的挡不挡」。所以补一层**真机实测**：`tools\authz-live.mjs` 读 `target\authz-matrix.json`，用三种身份打一遍。

```powershell
node tools\authz-live.mjs        # 日志 target\authz-live.log，末行给 VERDICT
```

判「被拒」的口径（这套代码的登录闸门有多种文案，只认 401/403 会把正常拦截误报成漏）：

- HTTP 401 / 403 / 302（重定向到登录页）；
- 或业务码 401 / 403；
- 或 **业务码 400 且消息含「未登录 / 请先登录 / 无权 / 没有权限」**——`Result.error("未登录")` 走的就是 code 400。

| 身份 | 目标 | 读数 |
|---|---|---|
| 匿名 | 非白名单的 141 条 | **141 / 141 被拒**，白名单 8 条可用（登录/注册/发码/改密/登出/困难等级字典/两个 health + 匿名默认头像） |
| 学生 chendw | 63 条员工专属路由 | **62 被拒 + 1 目标不存在**，0 条放行 |
| 教师 lisi | 12 条 `/api/admin/**` | **12 / 12 被拒** |

结论：**没有发现越权放行**（`VERDICT OK`）。脚本跳过的 2 条是静态首页 `/` 与 `@GetMapping({"", "/"})` 拼不出真实 URL 的多路径映射，已在日志首行写明。

一条观察项（不算放行，但写进来）：`GET /api/community/inspections/{id}` 学生访问他人记录得到的是 `404 检查记录不存在` 而不是 `403 无权`——服务层先判存在再判归属（`CommunityService.java` `inspectionDetail`）。这构成**弱存在性泄露**（能试出某个检查 id 是否存在），宿管检查记录本身敏感度低，选择保留现状并在此备案；若要收紧，把非员工分支改成「不存在与无权同答 404」即可。

另有三条实测事实（不是缺陷，免得下次又被当 bug 查）：

- 匿名 `GET /api/user/avatar` 返回**默认头像 SVG 226 B**，这是给未登录状态用的占位图，设计如此；
- 匿名 `GET /api/user/avatar/file/{filename}` 返回 403（D1 已修）；
- 匿名 `POST /api/user/avatar` 修 D2 之后是 `code 400 未登录`（修前 HTTP 500）。

## 11. 本次没做的（不夸大）

- **没有**把服务层守卫换成框架层：`hasAnyRole` 在这套没有 SecurityContext 的代码里会锁死所有人（见 §7）。本轮只补了 `ApiRoleGuardInterceptor` 粗筛（§7.1），**没有**引入 `UserDetailsService` / 完整 SecurityContext 鉴权，也没有给双用途路径加框架层保护（理由见 §7.1：会打断学生端，且那属于数据级归属）。
- **没有**给粗筛做「按角色整体收口」的等保口径映射：现在规则是「路径 → 允许角色」，不是「每个接口都声明所需角色」。要过等保测评，得先把角色模型（教师/辅导员/管理员/HOD 等）和接口清单对齐，是独立一轮。
- **没有**覆盖写操作的真机越权：真机矩阵对写接口只发空 body，能在守卫处被挡就够了；「写进去了但写错对象」这类由各模块单测的归属用例覆盖（`SecondClassServiceTest` 权限组 10 条、`VolunteerServiceTest` 18 条「无权」文案、`WorkstudyServiceTest` 403 组）。
- **没有**审计前端路由守卫：页面是静态 HTML，真正的门在接口层；页面直达只是「空壳」，数据要靠接口拿。
- **没有**修「板块停用后成绩单汇总仍保留该行」的口径差异（`SecondClassRecordMapper.xml` 汇总只过滤 `c.deleted=0`，未过滤 `enabled`）：故意保留——历史确认真实学分的行不该因为板块停用而消失，只是与学生端 `/categories` 只回启用项不一致，需要学校确认业务口径后再定。
